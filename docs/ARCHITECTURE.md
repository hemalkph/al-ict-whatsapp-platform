# Architecture

## Style

Modular monolith in one Next.js (App Router, strict TypeScript) codebase. No microservices.

## Layout

```
src/app/       routes only (UI and API handlers); thin, delegates to modules
src/modules/   domain modules, one folder each, public API via index.ts
src/shared/    small cross-cutting code (errors, logging); no domain logic
docs/          specs and ADRs
```

## Module boundaries

- A module exposes a public API through `src/modules/<name>/index.ts`.
- Code outside a module (including other modules and `src/app`) imports it only via `@/modules/<name>`.
- Files inside a module import their own internals freely.
- ESLint enforces this for files outside `src/modules` (`no-restricted-imports` on `@/modules/*/*`). Module-to-module deep imports are not lint-enforced yet: this is a convention, reviewed by humans. Do not add clever lint rules; if the rule gets brittle, keep the convention.

## Implemented modules

- `auth` (`src/modules/auth`): the two Better Auth instances built from one shared base configuration. Public API (`@/modules/auth`): `getAuth()` (public instance, the only one that may ever be HTTP-mounted), `getSession()`, `readAuthEnv()`. The private provisioning instance lives in `src/modules/auth/provisioning.ts`, is not exported from the barrel, and is import-restricted by ESLint to the auth and access modules.
- `access` (`src/modules/access`): fixed roles/permission matrix, `can`/`assertCan`, `requireUser`/`requireAccess`/`requirePermission`, `AccessContext`. Feature modules take an `AccessContext` and scope every query by `ctx.organizationId`.
- `whatsapp` (`src/modules/whatsapp`): webhook ingress (GET verification, exact-byte HMAC, raw body and per-item event storage, routing and idempotency; public API `handleWebhookGet` / `handleWebhookPost`), the PostgreSQL event queue and worker core (`queue/`), contact identity resolution (`identity/`), the MESSAGE and STATUS handlers (`inbound/`, `status/`), the opt-in standalone worker (`worker/`, started only by `npm run whatsapp:worker`) and the operator-only layer (`operator/`, used by `scripts/whatsapp-{accounts,events,status}.ts`). Everything except the two webhook handlers is internal to the module. Still not implemented: any call to Meta (outbound messaging, media download), identity-change handling, conversations / inbox UI. See `WHATSAPP_INTEGRATION.md`, ADR 0013 and `RUNBOOK_WHATSAPP.md`.
- Staff HTTP API: `src/app/api/staff/**` (5 route files) + `src/lib/route-helpers.ts`; routes call only the `@/modules/access` public API.
- Staff lifecycle services live in `src/modules/access/staff/` (re-exported from `@/modules/access`): createStaff, listStaff, changeMemberRole, suspendMember, reactivateMember, resetStaffPassword.
- Cross-cutting security helpers in `src/shared`: HTTP authorization errors and `toErrorResponse`, `emitSecurityEvent`, same-origin check, safe redirect validation.
- `src/app/**` may not import `@/db` or the private provisioner (ESLint).

## Routes and entrypoints

`src/proxy.ts` (optimistic cookie check), `/api/auth/[...all]` (public Better Auth instance), `/api/account/change-password`, pages `/login`, `/change-password` and the authenticated group `(app)` (landing at `/`, the staff inbox at `/inbox`). Operator CLIs live in `scripts/`: the auth ones call `@/modules/access/operator`, the WhatsApp ones call `@/modules/whatsapp/operator` (accounts, held and DEAD events, health) and `@/modules/whatsapp/worker` (the opt-in worker, `scripts/whatsapp-worker.ts`). The webhook endpoint is `/api/webhooks/whatsapp` (excluded from the proxy).

## Outbound messaging (Phase 05, backend only)

`src/modules/messaging` is a separate module from `src/modules/whatsapp` (the inbound module does not import it; a static test pins this). Public API: `submitOutboundMessage`, `getOutboundRequest` and two error classes. Two staff routes call it (`POST /api/conversations/{id}/messages`, `GET /api/outbound-requests/{id}`); they only queue and read. Sending happens in the opt-in `npm run whatsapp:outbound-worker` process (claim → SENDING → one HTTP request in `meta-transport.ts` → fenced record). `src/modules/messaging/meta-transport.ts` holds the only `fetch` to Meta in server code. See [ADR 0014](adr/0014-whatsapp-outbound-messaging.md).

## Staff inbox (Phase 06)

`src/modules/inbox` (public API `@/modules/inbox`) owns every inbox query and rule: the conversation list, conversation detail and contact panel, the message timeline, status and assignment changes (compare-and-set under the conversation row lock), per-staff seen state, internal notes, contact tags and quick replies. It takes only `@/modules/access` (authorization) and the read-only `getReplyReadiness` from `@/modules/messaging`; it has no network, transport or outbound-service import and cannot send (static tests). The other modules do not import it. Thirteen thin routes under `src/app/api/inbox/**` call it through `handleApi` (same-origin on mutations, `requireAccess`, safe errors). The page `/inbox` (`src/app/(app)/inbox/`) is a server component that renders the first page of data and hands over to a client component (`inbox-app.tsx`, with the list, timeline, composer, quick-reply picker and details panel); filters and the open conversation live in the URL. Replies use the Phase 05 endpoint only. Bounded polling refreshes the screen (no realtime service). See [ADR 0015](adr/0015-staff-inbox.md).

`src/modules/leads` (public API `@/modules/leads`, Phase 07B) owns the lead rules: manual creation, status changes (compare-and-set on a revision, under the contact's advisory lock and the lead row lock), the lead list, the lead detail with its attribution read model, lead history and the leads of one contact. It takes only `@/modules/access`; it imports no WhatsApp, messaging or inbox code, has no network code, and writes only `leads` and `lead_events`. Lifecycle timestamps are read from the database clock after the locks, never taken from the client (the closed time and a reopened cycle start keep a conservative later boundary only when a stored time is ahead of that clock; see ADR 0016). A lead write locks the actor's organization and then membership, the order staff management uses. Six thin routes under `src/app/api/leads/**` call it through `handleApi`. Automatic creation from ad referrals is the reconciler below (07C: implemented, undergoing independent review, not approved and not production-ready); the pages (07D) are not implemented. See [ADR 0016](adr/0016-leads-and-ad-attribution.md).

`src/modules/leads/reconcile` (Phase 07C) is the automatic lead reconciler: a bounded keyset scan of confirmed Meta ad touches of INBOUND messages that belong to the touch's OWN contact (`messages.conversation_id` → `conversations.contact_id` equal to the touch's `contact_id`, within the touch's organization) and that Phase 04 already stored (oldest first; decided touches, retries not yet due, contacts whose advisory lock is held by a session of THIS database, touches held back by the first-touch policy and touches of organizations that staff management holds exclusively are left out, the last by `FOR KEY SHARE ... SKIP LOCKED` on the organization row inside the scan statement itself, held only until the scan's own transaction ends and never across the per-candidate transactions), each handled in its own transaction under the contract lock order (organization `KEY SHARE`, a TRIED contact advisory lock, contact, open lead, touch, decision, history; no row lock is waited for) with its eligibility re-read under those locks. The fallible work runs in a savepoint inside that transaction: a recoverable failure is rolled back to the savepoint and its RETRY or PARKED row is written in the same transaction while the contact lock taken before the savepoint is still held, so no other reconciler can judge the touch in between. The attempt observes the touch's state before the work; after an ambiguous COMMIT (a lost acknowledgement) the fallback records a failure only if the committed state still equals the observed one, so one failure consumes at most one attempt. The run budget and batch size admit work (before every scan, page and candidate) and are not a deadline. Every statement runs under PostgreSQL's own lock and statement timeouts, set per transaction. It links a touch to an open lead at once or creates exactly one lead that names the touch (the database derives the cycle start), records skips as terminal decisions and failures as RETRY/PARKED, with the freshness anchor (the first-consideration time from the database clock, read while the contact is held) stored with the first failure. It is not exported from `@/modules/leads`; the only entry point is the opt-in command `npm run leads:reconcile` (`scripts/leads-reconcile.ts`), which runs one pass and prints counts. It imports no other module, has no network code and no scheduler, and is not production-ready (blocker 67). See [ADR 0016](adr/0016-leads-and-ad-attribution.md) and the runbook, section 9.

## UI component foundation (Phase 07D-0)

shadcn/ui is the component standard (ADR 0003). `components.json` (style `base-nova`, base `base`, Tailwind v4, aliases `@/components`, `@/lib/utils`) was already in the repository; Phase 07D-0 generated the first components into `src/components/ui/`: Button, Badge, Input, Label, Select, Table, Alert, AlertDialog, Skeleton, Separator, Toggle and ToggleGroup (Toggle is ToggleGroup's dependency). Nothing in the application imports them yet; the Phase 06 inbox, the login page and the header keep their own hand-written Tailwind and are unchanged.

- **The one new runtime dependency is `@base-ui/react`.** `base-nova` generates components on Base UI primitives (confirmed from the generated imports: `@base-ui/react/button`, `select`, `alert-dialog`, `separator`, `toggle`, `toggle-group`, `input`, `merge-props`, `use-render`). It supplies the accessibility behavior of Select, AlertDialog and ToggleGroup (labelling, focus trap and return, roving focus, Escape), which is why it is not replaced with hand-written code. Its optional peers (`date-fns`, `@date-fns/tz`) are not installed. Its own dependencies (`@base-ui/utils`, `@floating-ui/*`, `@babel/runtime`, `reselect`, `use-sync-external-store`) come with it. No Radix package is used.
- **Adding a component.** Run the shadcn CLI from a scratch directory with `--cwd` (running it through `npx` inside this repository fails with an unrelated npm error), preview with `--dry-run`, then apply and check three things: (1) the CLI resolves its `cn` utility to the unrelated npm package named `cn` (it installs it and imports `from "cn"`): uninstall that package and change the imports to `@/lib/utils`, as in Phase 01; (2) it does not install `@base-ui/react` by itself; (3) run Prettier over `src/components` (the generated files are not formatted for this repository).
- **Theme.** Only three light-theme tokens differ from the shadcn neutral defaults: `--primary` and `--ring` are the inbox's emerald-700 and `--primary-foreground` is white (`src/app/globals.css`). `--background`, `--foreground` and `--border` are untouched because the body inherits them. `--ring` also feeds the global `outline-ring/50` base rule, so the browser's default focus ring (elements with no explicit outline colour, such as the login fields and the Sign in and Sign out buttons) is now 50% emerald instead of 50% grey. Measured on the login, home and inbox screens at desktop and mobile widths: pixel-identical screenshots, and every computed style and element rectangle identical except that outline colour. There is no dark mode and none is added.
- **Behaviour to design around.** `AlertDialogAction` is a plain Button and does NOT close the dialog (only `AlertDialogCancel` does): control `open` and close it after the work succeeds, which is also what a pending or conflicting request needs. The dialog focuses the safe action (Cancel) first, traps Tab and returns focus to its trigger on close. `ToggleGroup` uses roving focus (arrow keys move between items, Tab leaves the group). Focus moves through a transient focus-guard element, so tests assert focus with `toBeFocused()` waits, never an immediate read. Select needs an accessible name (`Label` with `aria-labelledby`, or `aria-label`). A primary hover is always an OPAQUE colour (never `bg-primary/80`, which put white text at 3.68:1): Button and linked Badge mix `--primary` toward `--foreground` (light, 7.5:1) or toward `--background` under `.dark`; `src/components/ui/a11y-contract.test.ts` enforces 4.5:1 in both states. `ToggleGroup` forwards `orientation` to the Base UI primitive, so a vertical group navigates with ArrowUp/ArrowDown (the primitive renders `role="group"`, for which ARIA defines no `aria-orientation`).

## Shared lead UI logic (Phase 07D-1)

`src/app/(app)/leads/` holds the browser-side lead logic the Leads pages and the inbox lead card use (since Phase 07D-2 it is also the `/leads` route; see below). `lead-labels.ts` (status, state, source, origin, evidence and history wording; the six staff-settable statuses; reserved statuses displayable but never offered), `lead-filters.ts` (page URL <-> filters <-> the exact `GET /api/leads` query: "All" is the ABSENCE of `state`, `attribution=none` means "no Meta ad referral linked", not "no referral"), `lead-list.ts` (cursor "Load more": server order kept, duplicates collapsed, late or stale pages ignored, an empty page ends the list), `lead-api.ts` (typed wrappers for the six lead endpoints over the inbox's shared client, so the same timeout, abort, error codes and `X-Expected-Actor` protection apply; a Leads page must call `setPageActor` before its first request) and `lead-errors.ts` (each real error code mapped to a kind and a safe next step; `ACTOR_CHANGED` is its own kind, `STALE_STATE` means refetch, an uncertain mutation means check before acting, nothing retries). Types come from `@/modules/leads` with `import type` only; the status lists are copies pinned to the database enums by `src/modules/leads/ui-contract.test.ts`, which also checks every query and body against the server's own schemas.

## Leads page (Phase 07D-2)

`/leads` (`src/app/(app)/leads/page.tsx`, a server component) checks page access and `lead.read`, parses the filters from the URL with the 07D-1 utilities (unsupported values fall back to their defaults and never reach the API) and renders the first page from `listLeads` for the session's organization. `leads-app.tsx` (client) declares the page's actor to the shared client in a layout effect, before any request, and owns the interaction: the URL is the single source of truth for the filters (each change is a `history.pushState` entry, so Back/Forward restore it; a messy URL is replaced by its canonical form once); search is debounced (350 ms) and a draft shorter than 2 characters is shown but not searched; choosing a status shows the state as All, choosing Open/Closed clears the status. `lead-page-controller.ts` owns the request lifecycle: one current request; every new request, a block and leaving the page advance a sequence number, and a response is applied only if its number is current (on top of the 07D-1 key and cursor guards), so a late answer (A -> B -> A, a Load more after a filter change, anything after an actor change or unmount) is dropped even when it wins the race against its own abort. The first `ACTOR_CHANGED` (from any request of the tab) blocks the controller and replaces the page with a reload notice. The table is read-only: rows link nowhere until the lead page (07D-3) exists. The sidebar shows Leads only to roles with `lead.read` and marks the current section with `aria-current`; the page and its API authorize on their own.

## Lead page (Phase 07D-3)

`/leads/[id]` (`src/app/(app)/leads/[id]/`) is the read-only lead page. `page.tsx` (server) checks page access and `lead.read`, `contact.read` and `conversation.read` (the three `getLeadDetail` itself requires), loads the lead with `getLeadDetail(ctx, id)` and renders `LeadDetailApp` keyed by the lead id. The organization is the session's; a missing lead, a malformed id and another organization's lead all raise the same `NotFoundError` and end in the same `not-found.tsx` (same words, same response status), so nothing tells them apart. The query string carries only the list's filters: they are parsed and re-serialized by `lead-filters.ts`, so "Back to leads" can only ever be `/leads` plus canonical filters (a hostile value falls back to the defaults). The Leads table links each contact name to `/leads/<id>?<filters>` (a real link).

The detail response is used exactly as `LeadDetail` defines it: lead (status, state, origin, created / cycle start / last status change / closed times, `readOnly`), contact (profile name, last observed number, BSUID tail, first and last seen, archived), up to 10 conversations, attribution (source summary, evidence LINKED to the lead oldest first with the exact total, the latest linked touch, other evidence for the CONTACT newest first with the exact total and its recorded decision) and the first 20 history events with their cursor. Nothing is added to the API. The revision, `initiatingAttributionId` and raw ids other than the ones the page links with are not shown.

Client side: `lead-detail-app.tsx` declares the actor to the shared client before any request, subscribes to `ACTOR_CHANGED` and blocks the controller; `lead-detail-controller.ts` (outside React, the same one-current-request rule as the list controller) owns Refresh and "Load older events" (20 at a time, from the opaque cursor, duplicates collapsed, an empty page ends the list, a response for another lead is dropped, a refresh supersedes Load older, a failure keeps what is shown, 404/403 on a re-read replaces the page with the not-available notice); `lead-detail-sections.tsx` renders the sections; `lead-detail.ts` holds the pure paths, counts and facts. Evidence is shown in two separate groups ("Evidence linked to this lead", "Other evidence for this contact — not linked to this lead"). Ad headline, body, ids and link text are provider text: rendered as plain text in a box labelled "not verified", never as HTML, an `<a>`, an image or a redirect target, and nothing from them is requested (the server already reduces links to origin and path and returns only the end of the click id). The only links are the list, the Inbox (`/inbox?c=<conversationId>`, the inbox page's own deep link) and sign-in. There is no mutation, form or status control: the layout leaves the Status row for the 07D-4 controls. Busy buttons are `aria-disabled`, not `disabled`, so keyboard focus is not lost; when the last page of history is loaded focus moves into the history.

`SidebarInset` renders a `<div>` instead of the generated `<main>`: every page renders its own `<main>`, and nested main landmarks are invalid.

## Lead status management (Phase 07D-4)

The lead page (`/leads/[id]`) gained the staff status control. `POST /api/leads/:id/status` takes `{ to, expectedRevision }` (a strict schema: `to` is one of the six staff-settable statuses, `expectedRevision` an integer 0 or more); the server compares the revision under the contact's lock, refuses a stale one (409 `STALE_STATE`), a reserved lead (409 `RESERVED_STATUS`) and a reopening while the contact has another open lead (409 `ALREADY_OPEN`), answers `{ changed, lead }` (`changed: false` when the lead already had the status) and writes the status and its history row together. Nothing in the backend changed.

`lead-status-control.tsx` (Select of the six statuses, "Update status", a controlled `AlertDialog` for a closing or a reopening, and the message about what happened) is presentation only. Every decision and request is in `lead-detail-controller.ts`, which extends the 07D-3 controller instead of adding a second mechanism: the same one-current-request sequence, the same actor blocking, the same sticky `ACTOR_CHANGED` check before every request, and the same "answer for another lead is dropped" check.

- **A decision is bound to a revision.** Choosing a target records the revision shown; the confirmation dialog holds the same pair. The request sends exactly that revision (never read again at send time, never incremented in the browser). A read that brings another revision clears the choice and the dialog and says so (`decision_invalidated`): it is never sent with the newer revision. The status controls are unavailable while any request runs, so a refresh cannot arrive under an open dialog from the screen; the controller enforces it anyway (unit-tested).
- **One change at a time, never repeated.** A change is refused while anything else runs, a refresh and Load older are refused while a change runs, a second Confirm or Update does nothing, and the dialog stays open and inert (Cancel, Escape and a second Confirm are ignored) until the outcome is known. No failure, conflict or unknown outcome re-sends the change.
- **Outcomes.** `changed: true` is a confirmed success (the returned status and revision are shown at once; the closing time and history come from the read that follows). `changed: false` is shown as "no change". 409 `STALE_STATE`, `ALREADY_OPEN` and `RESERVED_STATUS`, 403 and 400 are refusals (nothing was saved). 401 asks to sign in. 404 hides the lead. 409 `ACTOR_CHANGED` blocks the page. A timeout, a dropped connection, a 5xx, an unreadable success or an unexpected error is an UNKNOWN outcome: said so, never repeated.
- **Read before deciding again (`needsRead`).** After every outcome except 401, the page reads the lead again (a read, never a repeat of the change) and the status control stays unavailable until that read succeeds. If the read fails the message stays (a confirmed change is shown as confirmed with unverified details; an unknown outcome stays unknown) and only the READ can be repeated ("Check the current state"). After `ALREADY_OPEN` the same read also asks `GET /api/leads/for-contact/:contactId` for the contact's open lead; the link to it appears only if the API names one that is not this lead.
- **An answer is believed only if it is the documented envelope** (`acceptStatusResult`): `changed` is a boolean; `lead` is an object for this lead whose status is the one asked for and whose revision is an integer, greater than the decision's after a change and equal to it when nothing was written; the few fields copied from it have the right type. The shared client only checks that a 2xx body is JSON, so a 200 such as `{ "changed": true }` can reach the controller: it proves nothing (the server may have committed) and is handled exactly like a lost answer, as an UNKNOWN outcome (never repeated, a recovery read, the control waits for it). Only the validated fields are copied into the page; a defect while applying a believed answer recovers the same way and is reported with `console.error`, so the page can never stay "changing". Reads and history pages are checked the same way (a malformed one is a failed, retryable read, never a page stuck "refreshing").
- **Messages are about the request.** "Your change to Qualified was saved" is a fact about the past; the lead's current status is the status control and history, from the latest read (someone else may have changed it since). The blocked notice after an account change says that a change submitted just before "may already have been saved"; it never says nothing was changed, because the server may have committed it before the page learned of the change.
- **History.** Never extended in the browser; it only changes with a read (a full detail read, which returns the history to its first page, as for Refresh).
- **Read-only.** No control for a viewer (`can.edit` false), a reserved or unknown status, or a read-only lead; the server enforces every one of these again.
- **Focus.** Busy buttons are `aria-disabled` (focus stays); after a confirmed change focus returns to the Select; after a conflict, a refusal or an unknown outcome it moves to the message; cancelling returns it to the Select.

Preliminary shell fixes of the same checkpoint (independent of status management): on a phone the sidebar sheet closes when a destination is chosen (`useSidebar().setOpenMobile(false)` in the click of each link), its Close control is no longer hidden, and the menu buttons carry no tooltip in the sheet (the tooltip trigger swallowed the first Escape); the Inbox's outer container is the `<main aria-label="Inbox">` and the conversation pane a `<section aria-label="Conversation">`, so the visible phone list has the page's one main landmark.

## Inbox lead panel (Phase 07D-5)

The Inbox details panel has a compact **Lead information** section under Contact (`src/app/(app)/inbox/lead-panel.tsx`), driven by `lead-panel-controller.ts`, which `inbox-app.tsx` owns for the whole page (it survives conversation switches). It reads `GET /api/leads/for-contact/:contactId` (the open lead, looked up on its own, and the newest 10 leads; `can.create` is `lead.edit` and not archived and no open lead) and offers one mutation, **Create lead** (`POST /api/leads`; 201 `created: true` or 200 `created: false` with the existing open lead). It has no status control: status changes stay on the lead page (07D-4).

- **Whose data.** A read is applied only if it is the newest read the controller started AND it is for the contact shown now (A -> B -> A drops A's first read); a body naming another contact is a failed read. Reads happen when a contact is opened (the Inbox passes "no contact" between conversations, so reopening reads afresh), on Refresh, and after a creation. No polling.
- **Creation is bound to its contact.** Switching conversations neither cancels nor redirects it; its outcome is stored for that contact and shown only while it is selected. The panel lists only what a read returned, never the creation's answer.
- **Unknown outcomes.** A lost answer, a 5xx, an unreadable 2xx or an envelope that is not the contract (`acceptCreateResult`: this contact's lead; `created: true` is NEW at revision 0; `created: false` is open) is an unknown outcome: never repeated, the contact is read, and creating waits for that read. The panel does not promise a rollback; repeating cannot create a second open lead (contact lock and partial unique index).
- **Lead ids are UUIDs, checked before they are trusted.** `isUuid` (in `leads/[id]/lead-response.ts`, shared by the Inbox panel, the Leads listing and Lead Details) mirrors the backend's `z.uuid()` as zod 4.6.5 implements it: versions 1-8 with the RFC variant in either letter case, the nil UUID, and the max UUID in LOWER case only; a unit test compares it with the backend schema over boundary samples. Every lead id in a read (`openLead`, each `leads[]`) and in a creation answer (`created: true` and `created: false`) must pass, or the whole body is refused: a read becomes a recoverable panel error (Try again is one GET, what was shown stays), a creation answer becomes an unknown outcome (recovery read, no repeat). A "non-empty string" test is not enough: a lone surrogate is a string, and building the lead link from it throws and takes the whole Inbox down.
- **Actor change.** Same shared client and `X-Expected-Actor`; `ACTOR_CHANGED` blocks the controller (data cleared, late answers dropped, nothing more sent). The Inbox notice is one fixed text that is true whatever was pending: the page stops using information from the previous session and sends nothing more; no new message was submitted after the change was detected; a message or a lead submitted before the change "may already have completed" and this page "cannot confirm its outcome". It never says nothing was changed or that anything was cancelled or rolled back, and it does not depend on a creation being in flight at that moment (the follow-up read of an answered creation is not a creation, yet the lead is committed).

## Final integration (Phase 07D-6)

No new feature: the finished Leads Management system verified as one workflow, and four small corrections.

- **One workflow, one source of truth per page.** Conversation -> Contact -> Lead information (Inbox, `GET /api/leads/for-contact/:id`) -> Lead Details (`GET /api/leads/:id`, history by cursor) -> Status (`POST /api/leads/:id/status` with `expectedRevision`) -> Leads listing (`GET /api/leads`). Each page reads the server when it opens, on Refresh, and after its own mutation; no page shares state with another and nothing polls the lead data. A status changed in Lead Details therefore shows in the Inbox panel and the listing the next time they read (open the conversation again, Refresh, or reload): the approved design, tested in `e2e/leads-integration.spec.ts`.
- **Lead ids are checked wherever they become a link or a key.** `isUuid` now also guards the Leads listing rows (`isLeadPage`, a failed read otherwise), Lead Details conversation and contact ids, and the id the ALREADY_OPEN lookup offers as a link. Lead Details' own id is not checked: it is the page's route id, compared with the id asked for.
- **Exact UUID parity.** The max UUID is accepted in lower case only, as zod accepts it; the first version of the mirror was case-insensitive and accepted `FFFFFFFF-...`.
- **Account-changed notice (Inbox).** One conservative text (see Inbox lead panel above); the title keeps "Your signed-in account has changed." because the other pages and many tests key on it.
- **Oversized webhook body.** The server refuses from the declared length and closes the connection (`Connection: close`, `handler.ts`) without reading the body. A client still uploading 4 MiB can see EPIPE/ECONNRESET before it reads the 413 (a reset discards unread data; RFC 9112 section 9.6). Not a webhook defect; no production change. The 4 MiB test accepts a reset ONLY with per-attempt evidence: the E2E harness (test-only, `e2e/harness/attempts.mjs`) records the status the server wrote for a request marked `x-e2e-attempt`, and the test requires that record to be 413 for that very request, whatever the client saw. A socket error with no such record (for example one raised before anything was sent) fails, as does any other status.
- **Lead Details reflow.** The page grid has an explicit `minmax(0,1fr)` column on phones; the implicit column grew with the rich lead's content (363px at 320px wide). The two-column layout from `lg` is unchanged.

Audit of the owner-added shell and Inbox look (not an approval of it): see the Phase 07D-6 report. Known limitations of the integrated system: lead data is read, not pushed (no polling, no cross-page sync); the Inbox panel lists the newest 10 leads of a contact; the app is light-only (the `.dark` tokens exist but nothing switches them); the CI `verify` job does not run `format:check`.

## Application shell and inbox look (Phase 07D UI update)

`src/app/(app)/layout.tsx` wraps every signed-in page in the shadcn sidebar (`src/components/ui/sidebar.tsx`, after the sidebar-07 block): `app-sidebar.tsx` shows the product and organization, a "Main" navigation with only pages that exist (Inbox; Leads for `lead.read`), and the signed-in name, role and Sign out (the same `SignOutButton`, which clears the browser's pending sends). It collapses to icons on desktop (its open/closed state is a display-preference cookie, `sidebar_state`, read by the server so the first paint matches) and becomes a sheet on phones; a slim top bar holds the toggle and the section name. ## Rules

- Outbound WhatsApp: only through the messaging service and compliance guard.
- Webhooks: verify signature, store the event, acknowledge fast, process asynchronously and idempotently (see WHATSAPP_INTEGRATION.md).
- Configuration is validated by the module that needs it, when it is implemented. There is no global env schema.
- Database access: standard PostgreSQL through Drizzle, no provider-specific coupling; hosting provider TBD (see DATABASE_DESIGN.md).

## Observability

Structured JSON logs with correlation ids (`request_id`, `organization_id`, `whatsapp_account_id`, `conversation_id`, `message_id`, `webhook_event_id`, `bot_session_id`). Never log secrets or unnecessary message content. `AppError` (`code`, `httpStatus`, `cause`) is the base error, enough to hook up Sentry later.
