# WhatsApp Cloud API outbound: evidence register

Phase 05. Every Meta-specific fact the outbound design depends on, what was verified, and what was not. Decisions that follow from it are in [ADR 0014](adr/0014-whatsapp-outbound-messaging.md). Inbound evidence is in [WHATSAPP_G0_EVIDENCE.md](WHATSAPP_G0_EVIDENCE.md).

**Retrieval:** official `developers.facebook.com` pages only, read through a fetch tool that converts the page and has a model extract it, so excerpts are tool-reproduced, not byte-exact. No message was sent and no Meta credential exists in this repository, CI or any test. Confidence: **VERIFIED** (official text, retrieved, consistent), **PARTIAL** (one retrieval, or the reference page is silent), **UNRESOLVED** (not established; the code is built so the unknown fails closed).

## What is deliberately not claimed

- The `recipient` request shape is documented by Meta but unconfirmed live and absent from the reference page. **Do not enable `WHATSAPP_BSUID_RECIPIENT_ENABLED` until a live test with a test number proves it** (approval-controlled; see the runbook).
- No sample of a real `sent`/`delivered` status for an outbound message was retrieved (inbound blocker 25 still applies).
- The error table lists a "retry" recommendation for the throttle codes but does **not** state that no message was created when it returns them. Throttle answers are therefore **not retried**: they are terminal UNKNOWN_OUTCOME until the contract is independently verified (blocker 41). Any answer that is not a well-formed documented error is treated as possibly accepted.
- Whether Meta may accept a message and still return an error or time out (so the message is delivered although our request "failed") is not documented; that is exactly why any outcome that could have reached Meta is `UNKNOWN_OUTCOME` and never resent.

## Policy assumptions needing owner approval

These are business decisions encoded conservatively because the platform has no approved policy. They are in `src/modules/messaging/eligibility.ts` and are safe to tighten, not to loosen, without a decision:

1. **UTILITY** templates are allowed only to a contact who has messaged this account before (any `last_inbound_at`). Rationale: no recorded business opt-in exists in the schema.
2. **MARKETING** templates require `contacts.marketing_consent_status = GRANTED`. The application never sets it (no consent capture exists yet), so marketing sends are effectively disabled.
3. **AUTHENTICATION** templates are unsupported (they need code-delivery handling and one-time-code semantics).
4. An expired window never converts to a template automatically; staff must choose a template deliberately.

## Evidence level of each claim

Three different kinds of statement are used in this project. They are kept apart so that policy is never mistaken for documentation.

**VERIFIED OFFICIAL BEHAVIOR** (retrieved from an official page; excerpts are tool-reproduced, not byte-exact):

- Endpoint, headers and the text and template request bodies (rows 1-3, 7); the success response shape and `message_status` values (row 4).
- The 24-hour customer-service window opens on a user message and resets on a new one; when closed only templates may be sent; the 72-hour free-entry window is separate (rows 5-6).
- The published error-code table, including the HTTP status and the "retry" hint per code (row 12); no `Retry-After` is mentioned (row 13); no idempotency key is documented for the send endpoint (row 11).
- BSUID addressing through `recipient` is _documented_ on the BSUID page, marked "coming soon" (row 9).

**PROJECT POLICY** (a decision of this application; not something Meta states):

- Free-form eligibility ends 10 minutes before the window would close; only inbound customer messages count.
- A stored phone number is never used for a contact that has ever been observed with a BSUID; only a never-BSUID contact is addressed by phone.
- Anything that may have reached Meta is UNKNOWN_OUTCOME and never resent (this includes every documented throttle answer); a refusal is believed only when it is a well-formed documented error with no success-shaped data. The only automatic repeats are refusals made before any HTTP attempt began (a gate, a missing credential, an invalid payload); a failure of the HTTP attempt itself (DNS, refused connection, TLS, timeout, reset) is UNKNOWN_OUTCOME.
- A template to a phone-only contact is sent only while a recent inbound keeps the window open (a historical phone and a historical inbound are not permanent identity or indefinite permission).
- The template and consent policy (UTILITY needs a prior inbound; MARKETING needs recorded GRANTED consent; AUTHENTICATION unsupported); operator-attested template approval.
- 4096-character text limit, 20 parameters × 1024, 1 s pacing, 5 attempts, 15-minute dispatch deadline, 60-second send-start budget, 5-minute recovery age.

**UNVERIFIED PROVIDER ASSUMPTION** (the design leans on it; nothing retrieved proves it):

- That the documented throttle codes (130429, 131056, 80007, 4) on a 429 mean no message was created (the table recommends retrying; it does not say this). **The design no longer relies on it**: those answers are terminal.
- That the `recipient` request shape works as the BSUID page describes (gated off).
- That Meta's limits (throughput, pair rate, text length) are not lower than the application's own limits.
- That a documented rejection code on a 4xx means no message was created.
- That the template approval an operator attests is true and current.

## HTTP client behavior (verified locally; this is not Meta documentation)

The send path was changed from Node's `fetch` to `node:https` `request` after this was reproduced on the project's runtime (Node 24.16.0, undici 7.25.0, 2026-10-11): a local server received one complete POST and answered HTTP 421; `fetch` then opened a second connection, which was refused, and reported `ECONNREFUSED`. Server-side counts: 1 POST received, 1 connection accepted; client-side error: connection refused. The same exchange through `http.request` returned the 421 with 1 POST and 1 connection. Consequences recorded as project policy:

- No network error code is treated as proof that nothing was transmitted; any failure of the HTTP attempt is UNKNOWN_OUTCOME.
- The transport is a single attempt (ADR 0014 section 4b), verified by `network.test.ts` and `network.db.test.ts` against real loopback sockets, not by an option of an HTTP client.
- This says nothing about how Meta's servers behave; it concerns only what our client may do on the wire.
