# WhatsApp Cloud API webhooks: G0 evidence register

Phase 04, checkpoint 1. This is the verification gate for every Meta-specific fact the webhook design depends on. Decisions that follow from it are in [ADR 0013](adr/0013-whatsapp-webhook-ingestion.md).

**Retrieval date: 2026-10-04.** Authority: official `developers.facebook.com` pages only. No third-party article was used to settle anything.

## Method and its limits (read this first)

- Meta rejects scripted HTTP requests (direct fetches returned an HTTP 400 error page), so every page was read through a fetch tool that converts the page to markdown and has a model extract or reproduce the requested part. "Verbatim" below means **as reproduced by that tool**, not a byte-exact copy.
- The tool contradicted itself on one hard point (H1). A separate web-search summarizer also produced statements that **no official page text supports** (a `system.previous_user_id` property and "there is no `user_id_update` field"). Search-summarizer output is recorded as `SNIPPET ONLY` and never counts as evidence.
- Some pages came back empty or refused verbatim reproduction (statuses reference, referral reference, the `user_id_update` reference URL, the legacy system-message page's JSON). Those are listed as gaps, not guessed.
- Confidence levels: **VERIFIED** (official text, retrieved verbatim by tool, consistent), **MEDIUM** (one retrieval, or consistent only by placeholder naming), **CONTRADICTORY** (official pages disagree), **SNIPPET ONLY**, **NOT FOUND**.
- Everything here must be re-read once more, by a person, in the full page before production use. The optional live smoke (ADR 0013) closes what no document can.

### H2. BSUID scope and cardinality: scope **VERIFIED**, simultaneous-validity **NOT DOCUMENTED**

Same page, "Business-scoped user ID" section.

> "BSUIDs are scoped to individual business portfolios. This means that any business phone number owned by a given portfolio can be used to message a BSUID scoped to the same portfolio, and attempts to message the BSUID using a phone number owned by a different portfolio will fail."

> "BSUIDs will be: generated automatically; prefixed with the user's ISO 3166 alpha-2 two-letter country code and a period, followed by up to 128 alphanumeric characters (for example, `US.13491208655302741918`); unique to each business portfolio-user pair; regenerated if a user changes their phone number (which triggers a system messages webhook)."

> "Your business portfolio will share a parent BSUID with other business portfolios that have been enrolled in the same parent BSUID account. WhatsApp users will be identified by the same parent BSUID across all enrolled business portfolios."

- Scope is the **business portfolio** (formerly Business Manager), not `phone_number_id`, and the page does not equate a portfolio with a WABA. Any number owned by the portfolio can message the BSUID, which supports "the same BSUID across all numbers of a portfolio" (MEDIUM: no sentence says it in so many words).
- A phone-number change **regenerates** the BSUID. Nothing documents whether the old BSUID stops working immediately, whether both are valid for a while, or whether a user can hold two BSUIDs in one portfolio at once.
- **Decision:** the "one current alias per contact" partial unique index is **not created** (the database must not assert what Meta does not document). It can be added later by a small migration once evidence exists. The application keeps at most one alias with `retired_at IS NULL` per contact and picks the newest `last_seen_at` if it ever sees more.
- Parent BSUIDs apply only to managed businesses enrolled in a parent-BSUID account (a Meta point of contact decides eligibility). They are not stored in Phase 04; they remain in the retained event payload.
- Onboarding invariant kept: **one application organization = one Meta Business Portfolio**. Required by `UNIQUE (organization_id, bsuid)`. Future change if an organization ever spans portfolios: add `business_portfolio_id` to `whatsapp_accounts` and `contact_bsuids`, and scope uniqueness to `(organization_id, business_portfolio_id, bsuid)`. WABA id is never substituted for the portfolio id.
- Timeline: "BSUIDs began appearing in webhooks in early April 2026" (one retrieval; MEDIUM).

### H3. contacts[] <-> messages[] pairing: rule **supported**, multi-sender shape **NOT documented**

- Every official example retrieved (text, image, video, audio, document, sticker, location, contacts, button, interactive, reaction, unsupported, referral, the BSUID examples) shows **exactly one `contacts[]` element and one `messages[]` element** in a `value`.
- Property definitions (BSUID page 13.2): `contacts[].user_id` = "User's BSUID (always included)"; `messages[].from_user_id` = "User's BSUID (always included)"; `messages[].from` = "User's phone number if available per conditions; omitted otherwise"; `contacts[].wa_id` likewise. The pairing key is therefore `from_user_id <-> user_id`, with `from <-> wa_id` as the fallback.
- Group webhooks do aggregate several contacts (status webhooks for groups) and incoming group messages carry `messages[].group_id` ("Group ID if incoming message sent in group").
- Generic Graph webhooks page: "Event Notifications are aggregated and sent in a batch with a maximum of 1000 updates." This is the generic Graph page, not a WhatsApp statement. No page documents ordering.
- **Rule kept:** primary `from_user_id <-> user_id`; fallback `from <-> wa_id`; never `contacts[0]`, never array position. `multi-sender-pairing.json` is `SYNTHETIC_EDGE_CASE`.
- Confidence: rule **VERIFIED by property definitions**; multi-sender shape **NOT FOUND** in official examples.

## Still unresolved after G0

1. **H1:** whether `user_id_update` is subscribable; which `system.type` values occur; whether any structured previous BSUID accompanies a system message; ordering relative to the user's first message under the new BSUID.
2. **H2:** whether an old BSUID stays valid after regeneration; whether two can be valid at once; BSUID equality across a portfolio's WABAs (supported, not stated).
3. **H3:** whether one `value` can carry several senders in a WhatsApp conversation.
4. Whether Meta sends escaped or literal UTF-8 on the wire (affects nothing in the rule, but is the one thing worth confirming with a real delivery).
5. Whether a reaction resets the 24-hour window; `source_type` values beyond `ad`; `nfm_reply` and `order` shapes; the `sent`/`read` status JSON; the entry-id/WABA relationship on a live delivery; which secret signs overridden-callback deliveries; Meta's per-request timeout.
