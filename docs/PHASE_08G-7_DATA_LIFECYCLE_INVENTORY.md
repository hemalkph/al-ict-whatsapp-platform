# Phase 08G-7 — Student data lifecycle inventory (for owner policy decisions)

Status: **READ-ONLY INVENTORY, DRAFT.** It was prepared from the committed migrations `0000`–`0009`, the schema and the source
(Phase 08G-7A). No database was queried. No retention period is proposed. Nothing was deleted, redacted or scheduled. The 30-day
session-redaction default (`0007` `bot_session_redaction_after()`) is unchanged. It feeds owner decision OD-G7-4 in
`PHASE_08G-7_READINESS_AUDIT.md`.

"Student personal data" here means anything that identifies or describes a student (or any WhatsApp user who writes in), or that
the student wrote: phone and WhatsApp identifiers, profile names, message text and media, typed names, years and class interest,
consent and lead records, and staff notes about them.

## 1. Flagged before any policy: Student Enquiry collects a name and a grade without a consent screen

`enquiryFlow` (`src/modules/bots/testing.ts`, test data, owner decision D-1) asks "What is your name?" (stored as `student_name`,
`sensitive: true`, up to 100 characters) and "Which grade are you in?" (`grade`, integer 1–13). It also sets `wants_call`. **No
consent or purpose statement comes before these questions.** Registration Enquiry, by contrast, asks for consent first (08G-5,
`consent` node). The name is then rendered into an outbound message ("Thank you, {{student_name}}. We will contact you."). So it
also persists in `messages`, `outbound_requests.payload` and the student's own inbound message (sections 2.2–2.4), not only in
the session variables that redaction clears.

This is test content, but it is the shape that production content would follow. **Owner decision needed (SE-2):** either Student
Enquiry collects no personal data (it hands "I want to join" to staff or points to the Registration keyword), or it gets a
consent step equivalent to Registration's. 08G-0 section 4 ("Only the Registration bot collects anything") already implies the
first option.

## 2. Inventory

Retention mechanism legend: **none** = nothing deletes or redacts it; **job** = an existing operator-invoked job that is not
scheduled anywhere (G7-5).

| Retention today        | **None** (blocker 9). `whatsapp:status` reports the volume older than 30 days                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                    |
| Deletion / redaction   | Feasible with care. `webhook_events` → `webhook_requests` is `NO ACTION`. `messages.source_webhook_event_id` and `message_status_events.webhook_event_id` → `webhook_events` are `NO ACTION`, so deleting an event is refused until those references are nulled. `contact_bsuids.source_webhook_event_id` is `SET NULL`. Deleting a `webhook_requests` row while any of its `webhook_events` remains is refused (`webhook_events.request_id` → `webhook_requests`, `NO ACTION`). `raw_body` is `NOT NULL bytea`: that forbids SQL NULL but **not** replacing the bytes with an empty value (`''::bytea`); no update trigger on `webhook_requests` was found in `0000`–`0009`. | Idempotency dependency | The ingestion duplicate check uses `webhook_events.idempotency_key`. Deleting the events earlier than Meta's redelivery horizon could let a redelivery be processed again. The inbound handler also checks the message wamid (section 2.2)                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                       |
| Policy options         | (a) delete the raw request after N days and keep event headers; (b) null the payload and keep the ids and key; (c) keep everything (status quo). Plus a separate rule for held and DEAD events                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                   |

| Purpose              | The staff timeline (the **only** staff-readable record of bot answers, 08G-0 L7), bot input, the unread state                                                                                                                                                                                                                                                                |

| Deletion / redaction | Deleting a row is blocked by `NO ACTION` references from `bot_triggers`, `bot_session_events`, `bot_sessions.started_by_message_id` / `last_input_message_id`, `message_reads`, `message_attachments`, `message_status_events`, `lead_attributions`, `outbound_requests` and `messages.reply_to_message_id`. **Redacting `body` / `content` in place** keeps every reference |

## 3. Owner decisions (unresolved; none proposed here)

1. **SE-2:** does Student Enquiry collect any personal data, and if so with what consent (section 1)?
2. Message text retention (inbound and outbound), and whether Registration conversations get a shorter period.
3. Expiry method: redact in place (keeps headers, references and idempotency) or delete (needs a cascade and a redelivery-safe
   horizon).
4. `outbound_requests.payload` retention after the request is terminal.
5. Raw webhook body and event payload retention, with the held and DEAD exemption.
6. Session variable redaction: keep the 30-day development default or set a production period (needs a migration).
7. Lifecycle and audit records (`bot_sessions`, events, triggers' 14 days, conversation events): retention or permanent.
8. Notes, contacts, consent and lead evidence: retention and erasure route.
9. Erasure requests from a student: supported or not, and the scope (including backups and Meta's copy).
10. Log and backup retention at the chosen host.
11. Registration consent wording, made consistent with decisions 2–9.
