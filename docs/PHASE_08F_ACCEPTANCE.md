## Browser acceptance plan (executed once in focused bots-only mode; see the run record below)

Infrastructure found (`playwright.config.ts`, `scripts/e2e.ts`, `e2e/support/*`, `scripts/e2e-seed.ts`):

- `npm run test:e2e` creates one disposable `al_ict_e2e_<random>` database through the shared guarded harness (admin URL from `TEST_DATABASE_ADMIN_URL` only, local host, PG 17 check), migrates, seeds, builds, serves over HTTPS with a throwaway certificate, runs Chromium, and drops the database in `finally`. It never reads `DATABASE_URL`. An `al_ict_e2e_*` database is therefore **required** for any browser run.
- Users and organizations are created by `scripts/e2e-seed.ts` (ORG_A..ORG_H; ADMIN, STAFF and VIEWER identities per area). Tests own distinct identities.
- Servers run with `WHATSAPP_LIVE_SEND_ENABLED=false`, no Graph version, no token, and no outbound or bot worker process. `WHATSAPP_OUTBOUND_ENABLED` is true only on the first server. Nothing can reach Meta.
- **Gap 1 (addressed in the uncommitted preparation, not yet executed):** `BOTS_*` is now a scrubbed family and `BOTS_RUNTIME_ENABLED` is pinned `"false"` for both servers. The build and Playwright children get `childEnv()` (`e2e/support/server-env.ts`), built only after the generated database exists: the application database is the generated one, the administrative URL, other `DATABASE_*`, `PG*`, Graph and Meta/WhatsApp names are blanked, and the three gates are explicit `"false"`. Hostile-environment unit tests cover this.
- **Gap 2 (addressed, not yet executed):** the bot fixtures are plain SQL (`e2e/support/bot-fixtures.ts`), written in one transaction after an identity check of the connection (exact `al_ict_e2e_<12 hex>` on 127.0.0.1:55432, PostgreSQL 17.x, guard triggers enabled). No production module is imported, so the `bot-control` boundary is unchanged. Each organization has its own bot, version and PAUSED deployment, and every session has its own awaiting token.
- **Bots-only mode:** `npm run test:e2e:bots` (`E2E_MODE=bots`) starts ONLY the outbound-off server and ONLY the `chromium-bots` project; the queue-enabled composer server does not run. `npm run test:e2e` is unchanged (both servers, all projects).

### History

1. First attempt: the first test failed because the server also reported `WHATSAPP_WORKER_ENABLED="false"` (from `.env.local`) and the spec compared the flags object exactly. Fixed by pinning that flag in the E2E environment and replacing the exact comparison with an all-flags-false check.
2. The reviewer found a P2 in the passing run, and a later ORDINARY-mode Playwright run (`npm run test:e2e`) reproduced it independently: `e2e/inbox-bot.spec.ts` unconditionally required the composer server's control port to be unreachable, which holds only in bots-only mode (the ordinary configuration starts the composer server alongside the bot project). The first bot test failed at that assertion and the ten later serial bot tests did not run; the screenshot is the only record. Corrected: the check runs only when `E2E_MODE=bots` (`isBotsOnly`, which refuses any mode other than empty or `bots`); the gate checks (`expectGatesOff`, at the start and end of the run), the worker and credential checks and the no-send comparison are unconditional, and the bot project is on the outbound-off server in both modes. Validated by database-free tests only. The corrected spec has NOT been re-run in either mode, so **full ordinary-mode E2E acceptance is not established**; the 11/11 focused result above remains valid for bots-only mode. The saved results of that ordinary run, and the working report directories, are not part of the archive below.
3. A controlled ordinary-mode run on 2026-10-28 (`npm run test:e2e`, one execution) produced 180 passed, 1 failed, 10 not run; databases cleaned up and the seven protected scratch databases unchanged. The composer-absence regression no longer occurred (the first bot test passed its gate checks), but it then failed at sign-in ("Invalid email or password") for the bot STAFF user, so the 11 bot tests did not run in ordinary mode. Root cause (established from source, not from the failure alone): the bot fixture copied the stored password hash of the seeded first admin, and `e2e/auth.spec.ts` changes that admin's password (to `E2E_NEW_PASSWORD`) in the same suite; Playwright does not order files, so the copy can happen after the change. In bots-only mode that spec does not run, which is why the focused run passed. Correction: the bot users now copy the hash of `INBOX_USERS.viewer` (`PASSWORD_SOURCE`), a seeded account created with the shared `E2E_PASSWORD` that no spec changes (only `auth.spec.ts` changes a password, and only the first admin's; no spec resets one). The fixture fails if that account is missing (no fallback). Validated by database-free tests of the actual writer bindings and of the specs' source; **not browser-validated**. Evidence: `/Users/hemal/phase08f-evidence/ordinary-run-2-2026-10-27/` (valid manifest excluding itself) and `ordinary-run-1-prior-failure/`.
