# ADR 0011: Database foundation conventions

Status: Accepted

## Context

Phase 02 introduces the PostgreSQL schema for the WhatsApp/lead foundation. The production hosting provider is still undecided (see ADR 0004); local PostgreSQL and a GitHub Actions PostgreSQL service are the only databases used in this milestone. Organization isolation (ADR 0005) must not rely on application code alone.

## Decision

- **Stack:** Drizzle ORM with node-postgres (`pg`). `pg` and the Drizzle driver adapter are imported only in `src/db/client.ts` (enforced by an ESLint `no-restricted-imports` rule); the database is reached through `@/db`. The schema is plain portable PostgreSQL, so the driver or runtime can be swapped later by changing `client.ts`. No provider-specific drivers or extensions.
- **IDs:** `uuid` primary keys generated by PostgreSQL (`gen_random_uuid()`). Cursors use `(timestamp, id)`, never ID order.
- **Timestamps:** `timestamptz` everywhere; event-time columns (`occurred_at`, `received_at`) are distinct from `created_at`; `updated_at` only on mutable tables. `archived_at` hides business entities reversibly. No blanket `deleted_at`. Privacy erasure is a separate, policy-driven workflow decided later (anonymization, hard deletion, media deletion, minimal retained proof); no retention periods are hardcoded.
- **Tenant isolation:** composite organization-aware foreign keys. Every parent has `UNIQUE (organization_id, id)`; children reference `(organization_id, parent_id)`. Messages additionally prove their account matches the conversation's, and a reply may only reference a message in the same organization and conversation. Webhook-event references are organization-aware too: `messages.source_webhook_event_id` and `message_status_events.webhook_event_id` reference `webhook_events (organization_id, id)`, so only events routed to the same organization can be referenced (unrouted events cannot). Status events must reference a message of the same organization and WhatsApp account, and a lead attribution's lead must belong to the same contact. FK actions are `NO ACTION` (no accidental cascades, no `SET NULL` on composite keys): retention cleanup of old webhook events must first null the referencing `webhook_event_id` columns in application-controlled code, then delete. Row-level security is deferred until authentication identity exists.
- **Constrained values:** `text` plus `CHECK`, with the value lists defined once in `src/db/schema/enums.ts`. No PostgreSQL enums. Open-ended sets (message type, webhook event type) have no CHECK.
- **Webhook inbox:** `webhook_requests` (delivery-level, no organization/account, only signature-verified deliveries) and `webhook_events` (one row per normalized item, nullable routing until resolved, unique deterministic `idempotency_key`, PostgreSQL-backed queue). Keys prefer provider identifiers; where a hash is unavoidable it uses deterministic canonical JSON (not plain `JSON.stringify`) and **includes the best available routing scope** (`phone_number_id`, else WABA ID) in the key, e.g. `hash:{event_type}:{phone_number_id}:{sha256}`, so identical bodies from different numbers never collide. The worker claims due PENDING/FAILED events and expired PROCESSING leases with `FOR UPDATE SKIP LOCKED`; both paths have partial indexes.
- **Message status:** `message_status_events` is append-only and authoritative; `messages.latest_status` is a cache updated by a conditional update using the priority `NULL < SENT < FAILED < DELIVERED < READ` (an event applies only if strictly higher). The result is order-independent and idempotent.
- **Consent:** append-only `contact_consents` plus a transactionally maintained cache on `contacts`. Organization-level for now; the design must not prevent account/channel-specific consent later.
- **Leads:** a contact may have multiple leads; no uniqueness constraint until offerings exist.
- **Migrations:** generated by drizzle-kit, committed, reviewed, forward-only. Schema push is never used. Production deployment of migrations is decided in the deployment milestone.
