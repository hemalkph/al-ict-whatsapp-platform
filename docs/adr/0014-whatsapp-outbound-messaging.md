# ADR 0014: WhatsApp outbound messaging

Status: Accepted for Phase 05 (backend only; no UI, no live send). Extends [ADR 0013](0013-whatsapp-webhook-ingestion.md). Evidence: [WHATSAPP_OUTBOUND_EVIDENCE.md](../WHATSAPP_OUTBOUND_EVIDENCE.md). Migration `0004`.

## Context

Phase 04 ingests inbound traffic. Phase 05 adds sending: staff reply to a customer (free-form text inside the 24-hour customer service window) or send an approved template. Meta documents no idempotency key for the send endpoint, so a request that may have reached Meta cannot be safely repeated, and a duplicate customer message is worse than a delayed one.

## Decisions

### 1. Pipeline

`staff API (queue only) → outbound_requests QUEUED → opt-in outbound worker → SENDING (committed) → Meta HTTP → fenced result record`.
The API route never sends and never imports the transport. The worker is a separate process (`npm run whatsapp:outbound-worker`), never started by the app, the build, a migration or a test.

### 2. Two independent real-send gates, exact `"true"`

`WHATSAPP_OUTBOUND_ENABLED` (queue and run) and `WHATSAPP_LIVE_SEND_ENABLED` (make real HTTP requests). Any other value, including `1`, `TRUE` or ` true`, is off. The worker refuses to start unless both are on; **the transport re-reads both on every send**, so a gate flipped off while running stops the next request even if a claim had already happened. A third gate, `WHATSAPP_BSUID_RECIPIENT_ENABLED`, guards the unconfirmed BSUID `recipient` shape. Nothing sends in tests: the transport takes an injected `post` function (or a loopback server in the network tests), and a static test pins that the only network implementation in server code is in `meta-transport.ts`.

### 3. State machine (enforced by a database trigger)

`QUEUED → SENDING → ACCEPTED | REJECTED | UNKNOWN_OUTCOME`, `SENDING → QUEUED` only for a refusal that came before any HTTP attempt began (a gate, a missing credential, an invalid payload, an abort signal already set, or the pre-send authorization), `QUEUED → HELD` for policy failures. ACCEPTED, REJECTED, HELD and UNKNOWN_OUTCOME are terminal. `outbound_requests_guard()` rejects any other transition and any change to an immutable column. Every post-claim update is fenced by `(id, state = 'SENDING', claimed_by)`, so a worker that lost its claim cannot write.

### 4. Duplicate prevention beats availability

`SENDING` with `send_started_at` is committed **before** the HTTP request. A crash, a lost connection or a timeout after that point leaves the request unrecoverable by design: a `SENDING` row older than 5 minutes becomes `UNKNOWN_OUTCOME`, and an HTTP timeout, a 5xx, a malformed response or any failure of the HTTP attempt is `UNKNOWN_OUTCOME`. **There is no automatic resend and no resend command.** The trade-off, stated plainly: some messages that were never delivered will be reported as unknown and need a staff decision (look at the WhatsApp Business Manager log, then send a _new_ request deliberately). We accept slower recovery to avoid ever sending a customer the same message twice.

Reconciliation has two cases that must not be conflated. (A) The answer carried the id `W` and a status or reply for `W` was processed before the answer was stored: that is repaired automatically when the acceptance is stored (section 9). (B) Meta accepted the message but the answer containing `W` was lost: the application never learns `W`, a later STATUS webhook for `W` cannot be matched to the request, and the status stays unlinked. There is no automatic recovery for case B; an operator verifies delivery in the WhatsApp Business Manager and decides (runbook section 7). No provider id is ever guessed or attached by hand.

### 4a. Claim time, claim authorization and what cannot be guaranteed

- **Time.** The claim transaction reads the clock _after_ every read that can wait on a lock (the account row is taken `FOR SHARE`, so a concurrent disable waits for or blocks the claim) and uses that reading for the dispatch deadline, the service window, the pacing check and `send_started_at`. Waiting is bounded (`lock_timeout`, 5 s); a request that could not be examined in time stays QUEUED, unchanged. A request whose window or deadline expired while waiting is HELD without sending.
- **Pre-transmission authorization.** Immediately before the HTTP request the worker re-reads its own row and sends only if it is still `SENDING`, still owned by this claim, younger than `SEND_START_BUDGET_MS` (60 s, far below the 5-minute recovery age), inside the dispatch deadline, the outbound gate is still on and the account is still ACTIVE. A worker whose claim was recovered, finished or taken by someone else sends nothing and writes nothing. A claim that is ours but must not be sent now (too old, deadline, account, gate) did not begin an HTTP attempt and goes through the normal not-sent path. The post-send fence (`id`, `state = SENDING`, `claimed_by`) stays, because it protects the other boundary: a late result can never overwrite a recovered request.
- **The transport makes at most one HTTP attempt per authorized invocation** (section 4b).
- **What this does not guarantee.** A database read cannot be atomic with an HTTP request, and no transaction is held open across the request. The 60-second send-start budget and the dispatch deadline are last evaluated during the pre-transmission authorization; they do **not** limit how long a process can stay suspended _after_ it (for example a stopped or frozen container). Such a process can resume after recovery has marked its claim UNKNOWN_OUTCOME (which can happen once the claim is 5 minutes old) and still start the request; there is no upper bound on that delay. The row then stays UNKNOWN_OUTCOME, is never retried by the application, and the late result is discarded by the fence, **but that late request can reach the recipient**. If an operator has meanwhile sent a replacement, both messages can arrive. Duplicate external sending is therefore **not** claimed to be impossible; it is made unlikely and visible, never ruled out.

**What is guaranteed, layer by layer, and what is not.** Exactly-once delivery is **not** claimed anywhere.

| Layer                                                                             | What it guarantees                                                                                                                                                                                                                                                                                         | What it does not                                                                                                                                                                                                                                                                                                                                                                                   |
| --------------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Request idempotency (unique key + fingerprint)                                    | One staff request creates at most one queued request; a replay returns the original                                                                                                                                                                                                                        | Nothing about delivery; a new key is a new request                                                                                                                                                                                                                                                                                                                                                 |
| Claim and fencing (`SENDING` committed first; result written only by the claimer) | Two workers cannot both own a request; a late result cannot overwrite a recovered one                                                                                                                                                                                                                      | That a claim holder is still alive                                                                                                                                                                                                                                                                                                                                                                 |

**Operating procedure before considering a replacement for an UNKNOWN_OUTCOME request** (runbook section 7): (1) stop or terminate the original outbound worker process; (2) verify that the original process cannot resume (not frozen, paused, detached or restartable under another supervisor); (3) investigate the available provider evidence (WhatsApp Business Manager message log, the customer conversation); (4) review whether a message may already have been delivered; (5) obtain an explicit operator decision. Even these measures do not provide mathematical exactly-once delivery, and no unrestricted resend command exists.

### 4b. The HTTP transport is a single attempt

**Defect found in review and reproduced** (Node 24.16.0, undici 7.25.0): a local server received a complete POST and answered HTTP 421; Node's `fetch` then silently opened a second connection, which failed with `ECONNREFUSED`, and that error was what `fetch` reported. The server saw 1 POST, the client saw "connection refused". Our classifier treated `ECONNREFUSED` as proof that nothing was sent and would have queued a second POST of a message the server had already received. Classifying the 421 correctly is not enough, because the replay happens inside the client.

**Decision.** Production code makes no use of `fetch`. `meta-transport.ts` sends with `node:https` `request` (`singleAttemptPost`), with a fresh non-keep-alive connection per attempt (`agent: false`). Node's `http(s).request` writes one request on one connection and reports what came back: it has no redirect, 421, 429, 5xx or reconnect logic, and the same local experiment returned the 421 to the caller with 1 POST and 1 connection. This was verified by running it, not assumed from an option: `network.test.ts` drives the real implementation against real loopback sockets (421 then a closed listener, 307/308, 429, 500, malformed 200, no answer, reset after receipt, truncated body, refused, unresolvable name, abort) and asserts, per case, what the server observed. The guarantee is **at most one** application-level HTTP POST per authorized transport invocation, not "exactly one": HTTP 421, 429, 500, a redirect, a malformed answer, a missing answer, a reset after receipt or a truncated body each show one received POST (and one connection); a refused connection or an unresolvable name shows zero received POSTs, because nothing reached a server. No failure is read as proof of either outcome: the classifier records every failure of the HTTP attempt as UNKNOWN_OUTCOME whatever the server observed. `network.db.test.ts` repeats the critical cases through the dispatcher on PostgreSQL, including a restarted dispatcher.

**What is preserved.** One fixed destination, `https://graph.facebook.com`, bound when the implementation is built (the URL's host is not used, and the production wrapper refuses any other origin, port or credentials in the URL before any network use); the Graph version and `phone_number_id` in the path; the token only in the `Authorization` header; Node's default TLS certificate-chain and hostname verification (nothing sets `rejectUnauthorized`; a test shows an untrusted certificate is never sent the request); no redirect is followed; request and response sizes are bounded (64 KB response cut-off); a hard total deadline (15 s) and the caller's abort signal; no body or token in logs. The only test seam is the `post` option of `MetaTransport`, which changes how bytes travel but not the gates, credentials or path; no production script passes it (a static test pins that).

**Classification.** A failure of the HTTP attempt (including DNS, refused connection, TLS, timeout, reset, abort, truncated response) is `UNKNOWN_OUTCOME` with a fixed reason (`transport_timeout`, `transport_network`, `transport_aborted`, `transport_response_incomplete`). An error code describes the last thing that went wrong, which may belong to a later connection attempt, so no code is read as "nothing was transmitted". We accept that this makes some undelivered messages UNKNOWN. The transport tells the dispatcher the moment an HTTP attempt begins (`httpStarted`); if any result claims `not_sent` or `throttled` after that, the dispatcher records UNKNOWN_OUTCOME (`result_after_http_started`) instead, so a fake, a bug or a future transport cannot assert proof about an operation it had already started.

### 5. Idempotent creation

Clients supply `idempotencyKey` (8–128 chars). Uniqueness is `(organization, account, membership, key)` in the database; creation takes an advisory lock `wa-outbound-idem:...`, compares a SHA-256 request fingerprint, replays the original result (HTTP 200) for the same payload and returns 409 for the same key with a different payload.

### 5a. Who may queue a message (staff authorization)

Written from the code (`route.ts`, `handleApi`, `requireAccess`, `submitOutboundMessage`); no authorization behavior is added by this phase.

- **Entry points.** `POST /api/conversations/{conversationId}/messages` and `GET /api/outbound-requests/{requestId}` both run through `handleApi`. There is no public or token-authenticated send path, and the proxy does not exempt them.
- **Session and membership.** The POST first applies the same-origin guard (state-changing request). Both routes then call `requireAccess`: a valid Better Auth session (otherwise 401), exactly one ACTIVE organization membership (none: 403; more than one: 409, because organization selection is not implemented and the system fails closed), and no pending forced password change (403 `PASSWORD_CHANGE_REQUIRED`).
- **Permission and roles.** `submitOutboundMessage` calls `assertCan(ctx, "conversation.reply")` before anything else. By the permission matrix (`permissions.ts`) `conversation.reply` is held by **ADMIN** (which has every permission) and **STAFF**; **VIEWER** does not have it and gets 403 with nothing written. Reading a request's status (`GET`) needs `conversation.read`, which all three roles hold. The matrix itself is unchanged by this phase.
- **Transactional actor revalidation.** The `AccessContext` was built before the transaction, so inside the transaction (before the conversation is read or anything is written) `revalidateActor` re-reads the membership by id, organization **and** user: it must still be ACTIVE and its current role must still hold `conversation.reply`, otherwise 403 `stale_actor`. A staff member who is demoted or suspended after the context was built is therefore refused.
- **Ownership comes from the database, never the request.** The organization is the one on the caller's membership. The conversation is loaded with that organization in the query: another organization's conversation and a missing one are the same 404. The WhatsApp account, the contact and the recipient are derived from that conversation; the request schema is strict and rejects `organizationId`, account, contact or recipient fields, and a body that contains `conversationId` is rejected (the id has exactly one source, the URL). Composite organization-aware foreign keys back this up in the database. The idempotency scope includes the requesting membership, so one staff member cannot replay or collide with another's key. The status view is read inside the caller's organization only and carries neither the recipient nor the message text.

### 6. Recipient identity safety

The recipient is derived from the database (the conversation's contact), never from the request. Decision table:

| Contact                                                      | BSUID sending disabled (default) | BSUID sending enabled (not verified; do not enable) |
| ------------------------------------------------------------ | -------------------------------- | --------------------------------------------------- |
| exactly one current alias (with or without a stored `wa_id`) | HELD `bsuid_send_unavailable`    | BSUID                                               |
| two or more current aliases                                  | HELD `identity_ambiguous`        | HELD `identity_ambiguous`                           |
| only retired aliases (with or without a stored `wa_id`)      | HELD `identity_ambiguous`        | HELD `identity_ambiguous`                           |
| no alias ever, intact `wa_id` (a legacy phone-only contact)  | PHONE                            | PHONE                                               |
| no alias, no `wa_id`                                         | HELD `no_identity`               | HELD `no_identity`                                  |

**A stored phone number is never a fallback for a contact that has ever been observed with a BSUID.** The Phase 04 resolver deliberately keeps a historical `wa_id` when BSUID observations change (it cannot tell a changed number from a recycled one, and it never reassigns aliases or merges contacts), so for such a contact the stored value is not evidence of who owns that phone number today, and nothing in the schema re-verifies it. Only a contact that has never been seen with a BSUID is addressed by the phone number Meta delivered on its inbound messages. No phone is derived from a BSUID or the reverse, no alias is reassigned, no contact is merged, usernames are never a target, and identifiers are used byte-for-byte (no trimming, normalization or truncation). The recipient is re-derived at claim time with the same rule; a change since creation (for example a BSUID observed after the request was queued) HELDs the request (`bsuid_send_unavailable`, or `recipient_changed` when the kind differs) and nothing reaches the transport.

### 7. Customer service window

Free-form text is eligible iff `now < min(last_inbound_at, now) + 24h − 10 min`. Only `conversations.last_inbound_at` counts: outbound messages, statuses, referrals and the 72-hour CTWA entry window never extend it; a stored inbound time more than 10 minutes in the future is `inbound_timestamp_invalid`. Checked at creation **and** again at claim. An expired window HELDs the request; it is never silently converted to a template. Outbound never changes `last_inbound_at`, `status` or reopens a conversation (it advances only `last_outbound_at` and `last_message_at` through `GREATEST`).

### 8. Scope and templates

Only TEXT and approved TEMPLATE. Templates come from a local registry (`whatsapp_templates`): `PENDING_ATTESTATION → APPROVED` only through `whatsapp:outbound templates approve --attest-approved-in-meta`, which records that an operator states Meta approved it; the platform cannot verify this. Policy (UTILITY needs prior inbound, MARKETING needs recorded GRANTED consent, AUTHENTICATION unsupported) is a conservative assumption listed for approval in the evidence register. **A template is a proactive message, and a phone number known only from inbound history proves who wrote then, not who owns the number now.** So a template to a phone-only contact is sent only while a recent qualifying inbound message keeps the 24-hour window open; with a historical inbound alone it is HELD with the window's own reason (`window_closed`, `no_inbound` or `inbound_timestamp_invalid`), even with recorded consent. This is checked at creation and again at claim. A recent inbound observation is sufficient local evidence for a phone-only reply (text or template) inside the ordinary window; a historical phone number and a historical inbound message are not permanent identity or indefinite permission. This is a **conservative project rule**, not a statement about Meta's technical ability to send an approved template outside the window (Meta allows it). Consequence: until a business decision defines what evidence may support a proactive template (blocker 44), no template can be sent outside the window. No consent is inferred or written.

### 9. Status reconciliation

On acceptance the worker takes the same per-message advisory lock the STATUS handler uses (`wa-message:{org}:{account}:{wamid}`), stores the wamid on the pre-created OUTBOUND message row, and calls the existing `resolveStatusEventsForMessage` in the same transaction. A status that arrived first (it was kept with `message_id NULL`) is linked; a status that arrives later finds the message. The same transaction then back-resolves earlier customer replies to this message with the existing inbound operation (`backResolveReplies`: same conversation and organization only, never to itself, never over an existing link). To make that race-free the inbound handler also takes the per-message lock of the wamid a reply answers (keys in sorted order), so a reply is either committed before the acceptance runs (and is back-resolved) or sees the stored wamid. Closes the Phase 04 contract recorded as blocker 24. This repairs only the case where the id is known; see section 4 for a lost id.

### 10. Provider answers, retry and rate limits

A request is recorded as definitively refused **only** when the answer is a well-formed Meta error object whose numeric code is in Meta's documented error table **and** the body carries nothing shaped like a created message (`messages` or `contacts` entries). An answer that came back from Meta is **never** put back in the queue. The only automatic repeat is a refusal made before any HTTP attempt began. A failure of the HTTP attempt itself is **never** read as proof that nothing was transmitted. Everything else is `UNKNOWN_OUTCOME`:

| Answer                                                                                                                      | Result                                                                                                                     |
| --------------------------------------------------------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------- |
| 2xx with exactly one intact message id and no error object                                                                  | ACCEPTED                                                                                                                   |
| any other 2xx (no id, two ids, unparseable, an error object next to an id)                                                  | UNKNOWN_OUTCOME                                                                                                            |
| 429 with a documented throughput/rate code (130429, 131056, 80007, 4), well formed, no success-shaped data                  | **UNKNOWN_OUTCOME** `rate_limited_semantics_unverified` (the code and HTTP status are kept; `Retry-After` is not acted on) |
| 429 with 131048 / 131049                                                                                                    | REJECTED `ecosystem_limit`                                                                                                 |
| bare 429, unparseable body, non-Meta body, undocumented or non-integer code, or success-shaped data                         | UNKNOWN_OUTCOME                                                                                                            |
| 4xx (not 408) with a documented rejection code and no success-shaped data                                                   | REJECTED                                                                                                                   |
| any other 4xx (including 421), a documented throttle code on a non-429 status, 408, 3xx, 5xx                                | UNKNOWN_OUTCOME                                                                                                            |
| refusal before any HTTP attempt began (a gate, a missing credential, an invalid payload, an abort already set)              | retried later (bounded)                                                                                                    |
| ANY failure of the HTTP attempt itself: name resolution, refused connection, TLS, timeout, abort, reset, truncated response | UNKNOWN_OUTCOME                                                                                                            |

**Why throttling is terminal.** Meta's error table recommends retrying the throttle codes, but nothing retrieved states that a request answered with one of them created no message, and the send endpoint has no idempotency key. Our approved priority is to prevent an unintended duplicate WhatsApp message even at the cost of automatic recovery, so those answers are treated like any response that may have been accepted. The switch is the code constant `THROTTLE_RETRY_VERIFIED` (`false`, in `policy.ts`): it is deliberately not an environment variable, the classifier and the dispatcher both enforce it, and a test-only dependency exists to exercise the preserved backoff machinery. Enabling it requires the Meta contract to be independently verified and a reviewed code change. The backoff infrastructure (5 attempts, 30 s base, ×2, capped at 15 min, ±20 % jitter, `Retry-After` capped at 1 h) and the application-side pacing (1 s per account and per conversation, our own limit) stay for that day and for the pre-attempt retries, together with the 15-minute dispatch deadline (then HELD `deadline_passed`).

### 11. Operator surface

`whatsapp:outbound` is read-only except template registration/attestation (dry run unless `--apply`): `health`, `counts`, `list`, `inspect`, `templates ...`. It prints no message bodies, recipient identifiers or provider payloads. No resend, no resolve, no replay.

### 12. Logging

Fixed-field events through `emitWebhookLog` only (`outbound.*`), carrying ids, state and reason codes. Never a token, body, recipient, template parameter or provider payload.

### 13. Phase 08D: bot requests (ADR 0020)

Requests now have an origin. STAFF requests behave as described above, with two deliberate changes:

- staff submission locks the conversation row first;
- the ACCEPTED record is retried, database-only, at most twice, on a deadlock or serialization failure raised inside it.

BOT requests (TEXT or INTERACTIVE, created only by `enqueueAutomatedMessage`) differ in four ways:

- they are claimed only while `BOTS_RUNTIME_ENABLED` is exactly `true`;
- they pass the bot rule `bot_request_hold_code` at claim and at a final authorization that also re-checks the window, contact
  and recipient with a fresh clock;
- they are never re-queued after their claim (HELD instead);
- they are suppressed by Stop through a non-blocking `SKIP LOCKED` primitive.

## Consequences

- Real sending needs two deliberate configuration changes and a separately deployed process; none exists yet.
- UNKNOWN_OUTCOME needs a human. This is the intended price of "never send twice".
- BSUID-only customers cannot be answered until the `recipient` contract is confirmed live and the gate is enabled.
- Marketing templates are effectively off until a consent capture feature exists, and no template can be sent outside the window until blocker 44 is decided.

## Rejected alternatives

- Retrying unknown outcomes after a delay (risks duplicate customer messages; Meta offers no idempotency).
- Using `fetch` with options to limit retries (an option was not shown to disable every internal replay, and the reproduced replay hid behind a different error).
- Sending from the API request (couples availability and duplicates to HTTP retries; long work inside a transaction).
- A resend/resolve operator command in this phase (needs an audit and identity design first).
- Deriving a phone number from a BSUID or vice versa (not possible, and unsafe).
