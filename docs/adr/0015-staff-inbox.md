# ADR 0015: Staff inbox and conversation management

Status: Accepted for Phase 06 (staff web UI over the existing inbound and outbound backends). Builds on [ADR 0012](0012-authentication-and-authorization.md), [ADR 0013](0013-whatsapp-webhook-ingestion.md) and [ADR 0014](0014-whatsapp-outbound-messaging.md). Migration `0005`.

## Context

Phases 04 and 05 give the platform a trustworthy inbound pipeline and a deliberately conservative outbound queue, but staff have no way to use either. Phase 06 adds the screen staff work in: a shared inbox (list, conversation, contact panel), replies through the existing outbound endpoint, and the team workflow around a conversation (status, assignment, unread, internal notes, tags, quick replies). It must not weaken anything Phase 05 decided: no second send path, no resend of an uncertain message, no message outside the policy.

## Decisions

### 1. Shape

A new `src/modules/inbox` module (public API: `index.ts`) holds every query and rule; thin API routes under `src/app/api/inbox/**` call it through `handleApi`; the page `/inbox` (server component) renders the first page of data and a client component takes over. No rule lives in a React component or a route. The module imports `@/modules/access` for authorization and, from `@/modules/messaging`, only the new read-only `getReplyReadiness` (so the composer can explain, before the user types, whether a reply would currently be allowed). Nothing in the inbox can send: a static test forbids any network, transport or outbound-service import in the module. The messaging and whatsapp modules do not import the inbox.

### 2. The composer reuses the Phase 05 endpoint

The composer calls `POST /api/conversations/{id}/messages` and nothing else; `pending-send.ts` (used by the composer) is the only UI file that mentions that path (pinned by a test). Authorization, recipient rules, the 24-hour window, templates policy, idempotency and the live-send gates are therefore exactly Phase 05's. The UI never describes a queued message as sent:

| Request state / provider status                         | Label shown                                                                                    |
| ------------------------------------------------------- | ---------------------------------------------------------------------------------------------- |
| QUEUED                                                  | "Queued": waiting to be sent; it has not been sent to WhatsApp yet                             |
| SENDING                                                 | "Sending…"                                                                                     |
| ACCEPTED, no provider status                            | "Accepted by WhatsApp": not yet reported as sent or delivered                                  |
| SENT / DELIVERED / READ / FAILED (from STATUS webhooks) | as reported                                                                                    |
| REJECTED                                                | "Rejected by WhatsApp" with the reason code                                                    |
| HELD                                                    | "Not sent" with the reason in plain words                                                      |
| UNKNOWN_OUTCOME                                         | warning: it may or may not have been sent; do not send it again until a supervisor has checked |

READ only ever appears when WhatsApp reported it. There is no resend, retry or "send again" control anywhere (pinned by a test); an operator follows the runbook. Idempotency in the browser is described in decision 2a below. In short: pressing Send freezes the message into an immutable pending operation (its own key, exact text, conversation); an answer that cannot be established leaves that operation on screen, across navigation and reload, and only an explicit click re-submits the same operation unchanged; the server's idempotency (Phase 05) is the authority that turns the repeat into the existing request. When outbound messaging is switched off (`WHATSAPP_OUTBOUND_ENABLED` not `true`) the composer says so and is disabled; the API refuses as before.

### 2a. Unresolved sends: the pending-operation journal (amended after the independent review)

**Problem.** The server can commit a request and the browser still not learn it (network failure or timeout after commit, a "success" whose body is truncated, cannot be read or does not match the contract, a 5xx, a reload or navigation mid-request). If the browser then treated that as a refusal, or forgot the idempotency key, the next Send would be a different logical request: a duplicate message.

**Three outcomes, never conflated.** (A) _Definitively refused before submission_: a 4xx the server issued. (B) _A validated success_: HTTP 200 or 201 whose JSON matches the Phase 05 contract exactly (`requestId`, `messageId` UUIDs, `state` one of the six request states, `replayed` boolean; a first-time answer must be QUEUED). (C) _Anything else_: network failure, timeout, 5xx, an unexpected 2xx status, an unreadable or truncated body, a body that fails the contract. C is **uncertain**; the UI never says the message was not queued.

**The operation.** On Send, `pending-send.ts` freezes `{version, user, membership, organization, conversation, idempotency key, exact text, reply target, created-at}` _before_ anything is sent and empties the draft. From then on the draft and the operation are separate: whatever is typed next is a new draft that no result can erase; a refusal returns the text to an empty draft, or shows it in the message when the person already typed something new. At most one unresolved operation exists per conversation; a second Send is refused until it is resolved or the person chooses to stop tracking it. The module (not the component) owns the request, so it completes and records its outcome even if the composer has unmounted.

**Where it lives.** In memory (survives in-app navigation) and in `sessionStorage` (survives a reload of the same tab; gone when the tab closes). Nothing is stored in `localStorage`. Records are strictly validated on read (shape, sizes, key format, UUIDs, and a tombstone may contain only its fixed fields); corrupt or oversized records are deleted, never shown. Records are scoped to user, membership and organization as the server rendered them for this page load. Message text is never logged and no token or cookie is stored. Unavailable storage (private mode, quota, blocked) is detected: the operation is still kept in memory, and the panel says plainly that a reload will lose track of it. Browser storage is never trusted for authorization.

**Retention, in three separate parts.** (1) _Sensitive payload_ (the exact text, the key, the reply target): kept at most 24 hours from when Send was pressed (`RETENTION_MS`; an operation is valid only while it is younger than that, so exactly 24 hours is expired). It is removed from memory **and** storage when the clock says so: on load, by a one-minute timer in a page that stays open, and on every focus, visibility, `pageshow` and `online` event, which is how a suspended or sleeping tab is re-checked the moment it resumes (browser timers do not advance while the machine sleeps, and no wall-clock guarantee is claimed for a suspended process). A payload past its retention is never sent, not even by _Check again_; an operation whose request is still running is re-checked when the request ends. (2) _Warning record_ (tombstone): in place of the payload, a record holding only the scope (user, membership, organization), the conversation id and two timestamps; no text, key, recipient or reply target. It is kept 7 days from submission (`TOMBSTONE_MS`) and dropped the next time the page loads after that. (3) _In-memory state_ is re-checked as in (1); an expired payload is not displayed. The 200-record capacity is a limit on **new** operations, never an eviction target (see "Identity and capacity" below). Expiry is **not** proof that the server request is absent: while a warning exists the conversation cannot be sent to, and the earlier submission cannot be reconciled because its payload is gone.

**Identity and capacity (journal integrity).** (1) _Identity._ A record is identified by `(user, organization, membership, conversation)`, percent-encoded and joined with `|`, and by nothing less. That one identity is the storage key (`al-ict.pending-send.v2:` + identity), the in-memory key, and what every read, create, update, tombstone conversion, acknowledgement, confirmed dismissal and removal uses; the identity embedded in a record must equal the one in its key. Two actors (same or different organization, same user with another membership) therefore never share a record for the same conversation, and one can never overwrite or delete the other's warning. (2) _Capacity._ At most 200 records (operations **and** unexpired warnings, of **all** actors in the tab) are supported. The check and the reservation of the slot happen in one synchronous step, before the operation exists and so before its request, which closes the check-then-insert race between near-simultaneous starts in a tab. A new operation at capacity is refused with a visible message ("Nothing was sent and nothing was deleted"); the draft stays as typed. Nothing is evicted to make room. Re-checking an existing operation needs no slot; an operation that becomes a warning keeps its one slot; only the person's confirmed dismissal or acknowledgement, or a warning's own legitimate end of life (7 days), frees one. Storage failure does not lift the limit (records kept only in memory still count) and never deletes anything already stored. (3) _Already over capacity._ A journal written by an older version may hold more than 200 valid records. All of them are kept and remain individually reachable; new operations are refused ("more unconfirmed messages than the 200 it is built to track") until enough are resolved. There is deliberately no bulk "clear all" and no way for one actor to discard another's records. (4) _Bounds._ At most 1000 storage keys are inspected (more means the journal cannot be verified and new operations are refused), and a stored value whose string length exceeds 32,768 characters (UTF-16 code units, not a byte count) is never parsed. (5) _Unreadable records._ A corrupt, tampered, mis-keyed or oversized record under a key that names an actor and a conversation is not forgotten: it becomes a text-free warning for that actor and conversation ("this device's record of it could not be read") that must be acknowledged; only a key that names no actor and conversation is removed. (6) _Migration from the previous format_ (key = conversation id only, written by the previous build of this phase): each valid legacy record is validated, converted under the same privacy and expiry rules (another actor's payload becomes a warning; a record whose 7 days are over ends), written under its actor-scoped key, and only then is the legacy key removed; a failed write leaves the legacy key and is retried on the next load; running it again changes nothing; an unattributable legacy record (unreadable, malformed identifier or mis-keyed: its key names no actor) is removed. _Logical equivalence_: two records are the same submission only when that can be **proven**, that is when both are live operations and every immutable field is equal (user, organization, membership, conversation, idempotency key, exact text, reply target). A timestamp is not identity (different submissions can share one, and the key is what makes the server treat two sends as one), and a warning has lost its key and text, so a warning is never provably equal to anything; two warnings are not either. When equivalence cannot be proven and both records still need protection, neither is dropped silently or overwritten, and neither is ever sent: they become **one blocking, text-free _conflict_ warning** that says "Conflicting local records were found for an earlier message submission. The original submission cannot be safely reconciled from this browser record", states that a message may already have been queued or sent, that a new one may be a duplicate, that nothing is cancelled and that a supervisor or operator may need to investigate. The idempotency keys of both are lost at that point (this is the loss of recoverable information the person is told about). Its life follows the **newest** involved submission (7 days from it), and a record whose own 7 days have already passed is simply ended and never shortens, expires or replaces a newer one. The conflict warning is acknowledged through the same confirmation as an expired one. No request is made by any of it.

_Malformed identifiers_: a stored identifier that cannot be percent-encoded (an unpaired surrogate), or a text that cannot be sent (the same), makes the record unreadable; building an identity from storage never throws. If the key is a valid canonical identity the conversation is blocked with an "unreadable record" warning for that actor (the record is not deleted for being malformed); a key that is not canonical names no one and is removed. _Retrying the removal of an expired payload_: when the warning that replaces an expired payload cannot be written, memory is already the warning (the stale operation cannot be sent, re-checked or reconciled) but the original payload may remain in `sessionStorage`; every expiry check (timer, focus, visibility, pageshow, online, and the start of a new send) tries the write again, once per check and never in a loop, and a reload replaces it as the record loads. Nothing is removed to do this, and if storage stays unavailable the bytes physically remain: deletion is not guaranteed in that case.

**Changing accounts: the server enforces it.** Idempotency (Phase 05) is scoped to the _membership_, so an old tab holding A's operation, with the cookie now B's (another tab signed A out and B in, both authorized in the same organization), would otherwise create a second request owned by B. Every inbox request therefore carries `X-Expected-Actor` (percent-encoded JSON `{userId, organizationId, membershipId}`): the actor the page was rendered for and, for a pending send, the operation's own frozen actor. `handleApi` compares it with the actor derived from the session, after authentication and before the route handler runs, and refuses a difference with `409 ACTOR_CHANGED` (fixed message, no identity). It fails closed (400) when the header is present but malformed, incomplete, oversized or repeated. It is an assertion, never authorization: the actor is always the session's, the permission checks and the transactional actor revalidation are unchanged, and stating one's own correct identifiers grants nothing. An absent header means no assertion (other callers of the Phase 05 endpoint are unchanged); the inbox always sends it (pinned by a boundary test). This holds for any tab, however stale, and for fresh sends as well as re-checks. On `ACTOR_CHANGED` nothing is submitted, the operation keeps its key and text, nothing is retried or moved to the new account, and the page replaces itself with a notice ("Your signed-in account has changed… No new message was submitted") and a reload button, so that stale content from the previous actor is not shown or used; polling stops. A browser cannot notice every cross-tab change instantly (the next request does); the guarantee is the server's. When a _different_ actor loads the page, the previous actor's payload is reduced to a text-free warning (that actor, signing back in, then sees the warning); if the original actor signs back in and reloads before anyone else loads the page, the operation is intact and _Check again_ returns the existing request. Explicit sign-out removes every record of the tab.

**Reconciliation (explicit, never automatic).** An unresolved operation is shown above the composer: "Your previous message may have been queued. Its result could not be confirmed.", with its exact text. _Check again_ re-submits the **same** operation (same key, same text, same reply target); the server returns the existing request (`replayed: true`) or, if it never committed, creates it. Nothing is sent on page load, navigation or reload. _Stop tracking this message_ is the person's own decision (they will check the conversation); it is the only way to a fresh Send. There is no read-only lookup by key because the platform exposes none and a request id is only known once an answer was read; a lookup would need a new endpoint and is listed as a blocker. After an earlier uncertain attempt, a refusal says nothing about that attempt unless it **proves** that no request exists: only a policy refusal (`OUTBOUND_REFUSED` other than `outbound_disabled`) is issued after the server looked the key up and found nothing. Switched off, expired session, forbidden, missing conversation: the operation stays unresolved and the message says the check could not be completed.

**Replayed state is reported as it is.** The notice after any answer follows the request's real state: QUEUED ("has not been sent yet"), SENDING ("being sent right now; result not known"), ACCEPTED ("does not mean it was delivered"), REJECTED, HELD ("not sent: on hold"), UNKNOWN_OUTCOME ("may or may not have been sent; do not send it again until a supervisor has checked"). An existing request is introduced as "Existing request found". Phase 05's UNKNOWN_OUTCOME stays terminal and has no control that could resend it; the browser's own uncertainty about an HTTP answer is a different thing and is never labelled with a backend state.

**Residual limits (not hidden).** There is no exactly-once guarantee across storage loss: a cleared or unavailable `sessionStorage`, a closed tab, explicit sign-out, another browser or device, a tab that is never reopened within 7 days, leaves nothing to reconcile from, and a fresh submission of similar text is then possible. Two tabs of the same user do not share records. Payload expiry (24 hours) turns reconciliation into a warning that the person must resolve by checking the conversation themselves. A server-side reconciliation (an idempotency-key lookup, or a per-conversation list of the member's recent requests) would remove these gaps; it needs a new endpoint and is recorded as a blocker rather than built here.

### 3. Schema (migration 0005, additive)

Two columns on `conversations` (`assigned_membership_id`, `assigned_at`, composite FK to the membership, CHECK that both are set or both null) and four tables, all organization-scoped with composite foreign keys: `conversation_events` (append-only history of assignment and status changes), `conversation_notes` (append-only internal notes), `quick_replies`, `message_reads` (per-staff seen state). Triggers make events and notes append-only. New indexes support "all/unassigned" ordering, "assigned to me", the unread subquery, the history and notes lists. Existing tables and migrations 0000-0004 are untouched; `tags` and `contact_tags` are reused as they are.

### 4. Status and assignment: compare-and-set under the conversation row lock

Both operations are transactions that (a) re-validate the actor against the database, (b) lock the conversation row `FOR UPDATE`, (c) compare what the browser last saw (`expected` status, `expectedAssigneeMembershipId`) with the row, and refuse with `409 STALE_STATE` if it differs, (d) write the change and one history row. The row lock is the same lock the inbound handler takes when it reopens a conversation, so a customer's new message and a staff action serialize instead of overwriting each other; a screen that still shows RESOLVED cannot overwrite what the customer just reopened. **What the check guarantees, and what it does not.** It compares the value the screen showed with the value stored now, under the row lock. It therefore refuses an action whose premise is no longer true (a screen that shows RESOLVED cannot overwrite a conversation the customer reopened; an assignment from a screen that shows "unassigned" cannot overwrite a colleague's). It does **not** detect every intervening change: a sequence that returns to the value the screen saw (OPEN → PENDING → OPEN, or the same for the assignee) leaves the stored value equal to the expected one, so the action is applied. That outcome is acceptable for these two fields, because the action is still correct relative to the state it is applied to, and the history table records every intermediate transition, but it is _not_ revision-based concurrency control. A version column that every writer bumps (including the Phase 04 inbound reopen, which this phase deliberately does not touch) would close the ABA case; it was rejected for Phase 06 and remains the upgrade path. Status: any change between OPEN, PENDING and RESOLVED; `resolved_at` is set when entering RESOLVED and cleared on leaving it (the inbound reopen rule compares it exactly as before). The transition time is read with `clock_timestamp()` **after** the row lock is obtained (not `now()`, which is the transaction's start and could predate a long lock wait) and one value stamps `resolved_at`/`assigned_at`, `updated_at` and the history row, so a customer message timestamped during the wait is correctly older than the resolution. Neither operation touches `last_inbound_at`, `last_outbound_at`, `last_message_at` or any message, so staff actions can never open or extend the 24-hour window.

Assignment: one current assignee or none, on the conversation row. An assignee must be an ACTIVE member of the same organization whose role can work conversations (`conversation.reply`: ADMIN and STAFF); the membership row is locked `FOR SHARE` so a suspension in flight waits. Every way of being ineligible (another organization's member, a suspended or viewer member, a member that does not exist) is the same refusal. A member suspended later **stays** assigned (never silently moved) and is shown as inactive; they can be replaced or unassigned, and the history keeps every change. Lock order is conversation then membership; the suspension code locks organization then membership and never a conversation, so there is no cycle with it or with the inbound and outbound handlers (which take advisory locks and then the conversation row, never a membership).

### 5. Unread is per staff member and per message

`message_reads (organization, membership, message)`; a row means "this staff member has seen this inbound message". Unread count = inbound messages that are not reactions or system notices, created after the member's own membership, with no row for that member, capped at 99 per conversation in the query. It is deliberately **not** a timestamp high-water mark: a message can commit late or carry an old provider time, and "everything up to time T" could hide a message nobody saw. The browser marks only messages that are **actually on screen**: the timeline reports, via an `IntersectionObserver`, the unseen inbound messages at least half visible (or half the viewport for a taller message), and only while the chat pane is really visible (not covered by Details on a phone or a narrow desktop, not a list-only pane) and the tab is in the foreground. A message a poll merely fetched, or one below the fold, stays unread until it is scrolled into view. There is **no dwell time**: a message that is at least half visible when the observer reports counts as seen, so scrolling quickly through a conversation can mark messages that were on screen only briefly (and a jump that skips content marks only what was actually rendered on screen). A minimum dwell would be a separate product decision. At most 100 ids per request; every id must be an inbound message of that conversation in that organization or the whole request is refused; marking is idempotent; a message that arrives meanwhile has no row and stays unread. Outbound messages, notes and status changes never count. A new staff member does not inherit the old backlog. This is internal bookkeeping: nothing is ever sent to Meta, so it is not a WhatsApp read receipt, and opening a conversation never produces a READ status. A VIEWER may mark their own seen state (personal state, not a change to the conversation).

### 6. Internal notes, tags, quick replies

- **Notes:** append-only rows with the author's membership; separate from messages; never part of any outbound payload; do not touch the conversation row. Reading and writing need `conversation.manage` (ADMIN, STAFF), so a VIEWER never sees them. Bounded to 4000 characters, plain text.
- **Tags:** existing tables. Attaching or removing a tag on a contact needs `contact.edit`; defining a tag needs `tag.manage`. The tag name is unique per organization ignoring case and spaces (database-generated key). Archived tags cannot be attached and are hidden from the picker; an existing link to an archived tag is still shown (flagged) and removable. Tagging touches nothing else: no identity, alias, consent, lead or message.
- **Quick replies:** organization-scoped reusable text (title up to 60, text up to 1000, unique among active ones, at most 200 active, enforced for creating **and for restoring an archived reply**, both under the same per-organization advisory lock). List and pick need `conversation.reply`; create, edit and archive need `conversation.manage`. A quick reply is not a Meta template: choosing one only fills the message box, and the Phase 05 policy still decides whether the message may be queued.

### 7. Authorization matrix

Every service checks its permission first and (for writes) re-validates the actor inside the transaction; the UI hides controls only as a convenience.

| Operation                                            | Permission                      | ADMIN | STAFF | VIEWER |
| ---------------------------------------------------- | ------------------------------- | ----- | ----- | ------ |
| list / open conversations, timeline, accounts filter | `conversation.read`             | yes   | yes   | yes    |
| mark own messages seen                               | `conversation.read`             | yes   | yes   | yes    |
| change status, assign, list assignees                | `conversation.manage`           | yes   | yes   | no     |
| read / write internal notes                          | `conversation.manage`           | yes   | yes   | no     |
| list / pick quick replies                            | `conversation.reply`            | yes   | yes   | no     |
| create / edit / archive quick replies                | `conversation.manage`           | yes   | yes   | no     |
| attach / remove a contact tag, list available tags   | `contact.edit`                  | yes   | yes   | no     |
| create a tag                                         | `tag.manage`                    | yes   | yes   | no     |
| queue a reply                                        | `conversation.reply` (Phase 05) | yes   | yes   | no     |

Mutations are same-origin only (the existing guard). Another organization's id is the same 404 as a missing one.

### 8. Display of untrusted text

Profile names, usernames, message bodies, captions, filenames, template names and parameters, and note text are returned as plain strings, truncated, and stripped of control characters, bidirectional embeddings/overrides/isolates (which can reorder text to impersonate someone), the zero-width space and the BOM. The zero-width joiner and non-joiner are **kept**: Sinhala and Tamil words need them (an earlier version stripped them and mangled "ශිෂ්‍යයා"; a test now pins it). React renders everything as text; no HTML is built from content (a test forbids `dangerouslySetInnerHTML`). Unsupported types show a placeholder; shared contact cards are not expanded; attachments show metadata and their state (not downloaded / no longer available) but no storage key, media id or URL. Contacts are not verified identities and not necessarily students: the panel says so, flags a stored phone number on a contact that was later seen with a BSUID as "may not belong to them now" (Phase 05 never sends to it either), and shows only a short tail of identifiers in the list.

### 9. Listing and pagination

One query per page: keyset pagination on `(last_message_at DESC, id DESC)` (the effective activity time written by the inbound handler, capped at receipt + 5 minutes for future provider times), cursors carry the exact PostgreSQL microsecond text (and each list row exposes it as `activityKey`, the key the browser sorts and merges by), lateral joins give the latest-message preview and the unread count (no N+1), filters (status, mine, unassigned, unread, WhatsApp number) and a bounded search (2-64 characters; name and username by `ILIKE` with wildcards escaped, phone id by prefix, BSUID by exact match). Messages page the same way on `(occurred_at, id)`, scoped by organization, conversation and the conversation's account. A late message with an old provider time appears on reload, not inside already loaded older pages; this is a documented limitation of keyset paging.

### 10. Refresh: bounded polling

No new infrastructure. The list refreshes every 15 s and the open conversation (messages, delivery states, reply readiness, notes) every 5 s (`INBOX_POLL_LIST_MS`, `INBOX_POLL_CHAT_MS`; clamped to 3-300 s and 2-120 s, invalid values fall back to the defaults). A run is scheduled only after the previous one finished (no overlap or storms); a hidden tab makes no requests at all (its timer only wakes at a tenth of the rate and does nothing) and refreshes at once when it becomes visible; nothing runs while offline; timers and requests are cleaned up on unmount; refreshes merge by id (no duplicates, scroll position kept unless the reader is at the bottom) and never touch the composer's text. Refreshes of the same kind are coordinated by a _latest-started-wins lane_ (list; open conversation): starting a request aborts the previous one and a response is applied only if no newer request of its lane started meanwhile, so a slow poll that began before a status change cannot bring the old status back, and a response for one conversation cannot land on another (selecting, going back and unmounting cancel the lane). The list merge compares the full server ordering tuple `(last_message_at at microsecond precision, id)` and keeps every loaded row that sorts after the refreshed first page, including rows that share the boundary's timestamp. "Try again" after a failed load starts a real new request. Trade-off: staff may see a new message up to 5 s late and the database sees a small constant load per open inbox. Upgrade path if that stops being acceptable: server-sent events driven by PostgreSQL `LISTEN/NOTIFY` from the same transactions, keeping the polling as the fallback; no change to the data model.

### 11. Out of scope (unchanged)

No bot, automatic replies, bulk messages or campaigns, lead pipeline, student records, payments, media download or upload, Flows, customer-data export, Meta credential screens, new realtime service, or deployment. Templates outside the 24-hour window stay blocked by the Phase 05 rule (blocker 44); the inbox does not work around it.

## Consequences

- Staff can run the day-to-day workflow; the safety model of Phase 05 is intact because the UI has no way to bypass it.
- A conversation changed from a stale screen is refused with a clear message instead of overwritten.
- Per-message read rows grow with staff × inbound messages; acceptable for the expected size, a retention job is a pre-production item.
- Notes and history are append-only, so removing personal data later needs a deliberate migration that disables the trigger.
- Polling latency and a plain `ILIKE` search are known limits (blockers 47, 48). The pending-operation journal is client-side continuity, not durable reconciliation (blocker 55).

## Rejected alternatives

- A version column on `conversations` (would need the inbound handler to bump it).
- A "last read at" timestamp per member (hides late or out-of-order messages).
- Browser storage for unread state (not shared across devices, not per staff member on the server).
- A separate assignments table (the current assignee is a single fact; the history table keeps the changes).
- WebSockets or a hosted realtime service (a new moving part for a few staff).
- A resend or "try again" button for held or uncertain messages (Phase 05 forbids automatic and unrestricted resend). The _Check again_ control of decision 2a is not that: it can only repeat the identical submission, which the server turns into the existing request.
- `localStorage` for pending operations (survives the session and is shared between tabs and users of the browser profile; `sessionStorage` is tab-scoped).
- Re-sending automatically when the browser cannot read an answer (a repeat must be a person's explicit decision).
- Cleaning the zero-width joiner out of text (breaks Sinhala and Tamil).
