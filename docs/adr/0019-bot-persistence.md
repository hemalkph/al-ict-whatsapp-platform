# ADR 0019: Bot persistence, versioning and state controls (Phase 08C)

Status: Accepted for Phase 08C (implemented; independently approved, owner-reported). Implements the 08C checkpoint of the Phase 08-0 V3.2 proposal (sections F, G, J.1, K, K.10, K.11, L, P) following the corrected, independently reviewed 08C implementation plan. Builds on [ADR 0011](0011-database-foundation-conventions.md), [ADR 0012](0012-authentication-and-authorization.md), [ADR 0017](0017-bot-flow-contract.md) and [ADR 0018](0018-bot-execution-engine.md).

Review reconciliation (Phase 08E-0.1): the earlier awaiting-review status is superseded by the owner's report of independent approval. Reviewer identity, approval URL and exact review date were not supplied; see the [review status and evidence record](../PRE_PRODUCTION_BLOCKERS.md#phase-08-review-status-and-outstanding-testing-conditions). Review approval is distinct from testing-condition closure (all three Phase 08D conditions are now CLOSED following owner-reported final Phase 08E-0 independent acceptance) and from production or automation authorization.

## Context

The pure contract (08A) and engine (08B) need durable drafts, immutable published versions, deployments with stop fences, a session table whose terminal rows cannot be rewritten, the per-conversation control sequence and a restricted privacy redaction, before any runtime (08E) writes a session or the dispatcher (08D) sees a BOT request. 08C builds these as database guarantees, plus the management services and an operator command line. Nothing in 08C sends a message, runs the engine or calls Meta.

## Decisions

### 1. Migration 0007 and its scope

`0007_bot_foundation.sql` (generated by drizzle-kit, then edited by hand in three marked places) creates `bots`, `bot_versions`, `bot_deployments`, `bot_deployment_events`, `bot_sessions`, `bot_session_events` and `bot_triggers`, adds `conversations.control_seq bigint NOT NULL DEFAULT 0` and the unique `(organization_id, id, contact_id)` on `conversations`. Migrations 0000-0006 and their snapshots are unchanged (pinned by SHA-256 in a boundary test). Hand edits: a preflight (refuses a non-UTF8 server encoding; `SET LOCAL lock_timeout = '5s'`, because adding a column and a unique constraint to `conversations` needs table locks: run it in a planned window), the `conversations` unique moved before the foreign key that references it (drizzle-kit emits it last, which would fail), and the functions and triggers appended at the end. The Drizzle migrator runs all pending migrations in one transaction (verified in `drizzle-orm/pg-core/dialect.js`), so `SET LOCAL` applies.

### 2. Canonical configuration storage (plan correction 1)

The 08A contract limit is 65,536 UTF-8 bytes of the canonical (RFC 8785) JSON. PostgreSQL's own jsonb rendering is a different representation (spaces; exact decimal expansion: the valid coordinate `5e-324` is 6 canonical bytes and over 320 rendered characters), so **no CHECK ever measures jsonb text**.

- **Drafts** are stored as canonical text only (`bots.draft_config_canonical`; an amendment of K.1's `draft_config jsonb`): `octet_length(...) <= 65536`, and a trigger requires it to parse as `json` (not `jsonb`, which refuses `\u0000` an unfinished draft may contain). The service writes exactly `canonicalJson(config)` after `checkJsonShape` and an exact byte check.
- **Versions** store `config_canonical text` (`octet_length` BETWEEN 2 AND 65536), `config jsonb` and `config_sha256`, all NOT NULL. The insert trigger refuses unless `config IS NOT DISTINCT FROM config_canonical::jsonb`, `config_sha256 = encode(sha256(convert_to(config_canonical, 'UTF8')), 'hex')` and `schema_version` matches. Each version's jsonb is bounded because it equals a canonical text of at most 65,536 bytes; no separate resource ceiling is needed.
- The migration refuses a non-UTF8 database, where `octet_length` would measure something else.
- The database proves the text, the jsonb and the hash agree; it cannot prove the text is RFC 8785 canonical. That stays the application's job (the services write only `canonicalJson` / `canonicalFlowJson` output; pinned by unit tests).

### 3. Authorization sequence (plan correction 2)

Every bot write runs `write()` in `bot-control/common.ts`: `assertCan` fails fast; then one transaction locks the organization `FOR KEY SHARE` and the actor's membership `FOR SHARE` (`lockAndRevalidateActor`, a new additive helper in `access/staff/guards.ts`; `revalidateActor` and its callers are unchanged), validates status and permission from that locked row, and only then takes domain locks. Staff suspension and role changes lock the organization `FOR UPDATE` first, which conflicts with `KEY SHARE`: a revocation that committed first is seen and refused; a later one waits until the bot write commits. Two bot writes of one organization do not block each other on these locks. (The leads module uses the same pattern privately in `leads/locks.ts`; consolidating it onto the access helper is a later cleanup.)

Domain lock order (V3.2 L.2): admin operations lock the bot, then the deployment; Stop / Emergency Stop / Retire lock the deployments (id order), the conversations of their live sessions (id order), then the sessions (id order). A session is never updated without its conversation locked first.

### 4. Sessions: NULL-safe state rules (plan correction 3)

Every state-dependent CHECK is written `(...) IS TRUE` or uses NOT NULL columns, because PostgreSQL accepts a CHECK that evaluates to NULL:

- terminal notice: `terminal_notice_step_seq IS NULL OR (terminal_notice_step_seq = step_seq AND state IN ('COMPLETED','HANDED_OVER') AND end_reason IN ('flow_end','flow_handover')) IS TRUE`; a NULL, system or error reason can never authorize a notice;
- a terminal state has `end_reason` and `ended_at`; a live state has neither;
- `COMPLETED`: `flow_end`, `idle_timeout`, `conversation_resolved`, `error`; `HANDED_OVER`: `flow_handover`, `system_handover`, `error`; `FAILED`: `error`;
- `handover_reason` exactly when `HANDED_OVER`; for `flow_handover` one of the configurable HANDOVER reasons (`BOT_FLOW_HANDOVER_REASONS`, kept equal to the engine's `HANDOVER_REASON_CODES` by a unit test), otherwise a system reason; `handover_control_seq` exactly when `HANDED_OVER`;
- `variables` NOT NULL and a JSON object; `awaiting` SQL NULL or a JSON object (JSON `null` is refused); tokens match the 22-character grammar.

The guard (`bot_sessions_a_guard_trg`) admits inserts only in a live state without end, notice, handover, suppression or redaction fields and stamps `started_at`; on a live row it keeps ownership, bot, version, deployment, conversation, starting message, `started_control_seq` and `started_at`, requires `revision + 1`, sets `output_suppressed_at` once, keeps `redacted_at` NULL, and stamps `ended_at` with `clock_timestamp()` on the move to a terminal state (so retention can never be shortened by backdating); on a terminal row it allows only a no-op or the K.11 redaction (whole-row comparison). There is no `updated_at` on `bot_sessions`: an automatically changed timestamp would turn every no-op into a forbidden terminal change.

A session that starts at END or HANDOVER is inserted live (`ACTIVE`) and made terminal with its notice in the same transaction (the engine returns it already terminal; 08E maps it). The engine's `expiresAt` (epoch ms) maps to `expires_at`. `transition_count` is a column (the engine's 200-transition budget needs it; G.5 does not list it).

### 5. Control sequence (V3.2 J.1, K.10)

`allocate_conversation_control_seq(org, conversation)` is the only writer of `conversations.control_seq`: one `UPDATE ... RETURNING` under the conversation row lock (values follow commit order; a rollback leaves nothing; no other column, so Inbox ordering is unchanged), raising `foreign_key_violation` for a conversation outside the organization. Triggers allocate `started_control_seq` on insert and `handover_control_seq` on the live -> `HANDED_OVER` update (never a redaction), overwriting application values. Triggers fire in name order: `bot_sessions_a_guard_trg`, then `bot_sessions_b_allocate_*`; the guard leaves the allocator-owned columns to the allocator and the table CHECKs validate the final row. The staff-table allocation triggers are 0008 (08D).

### 6. Versions, drafts and deployments

- Versions are insert-only (UPDATE and DELETE raise); `published_at` is stamped by the database; numbers are max + 1 under the bot lock, backed by a unique constraint. A publish names the draft revision the publisher reviewed: exactly that draft is published, or nothing.
- A draft change increments `draft_revision` by exactly 1 (the service's compare-and-set is backed by the guard) and is stamped by the database; a draft is never removed. Saving content whose canonical text equals the stored draft (including JSON that differs only in key order) is a successful no-op after the revision check: the revision, metadata and row stay unchanged and nothing is audited; a stale revision is still refused.
- Deployments are inserted `ACTIVE` at epoch 1; organization, account and bot never change; `send_epoch` never decreases and rises by exactly 1, and must rise when the status becomes `STOPPED` or `RETIRED`; `RETIRED` is terminal and immutable; nothing is deleted. The database stamps `status_changed_at` and `start_eligible_from` (every activation or resume) and `activated_at`.
- Whole relationships are foreign keys: a session's conversation, account, contact, starting and last input messages, bot, pinned version and deployment all agree (including `(organization_id, deployment_id, whatsapp_account_id, bot_id)`), and the pinned version is independent of the deployment's current version; a deployment's version belongs to its bot; triggers and events bind their message and session to the same conversation.

### 7. Stop, Emergency Stop and Retire (state only)

Stop Active Sessions (per deployment): `PAUSED`, epoch + 1, every live session `HANDED_OVER` (`system_handover`, `operator_stop`) with `output_suppressed_at` set, `awaiting` and tokens cleared, a `HANDED_OVER` session event and a `SESSIONS_STOPPED` deployment event. Emergency Stop: every `ACTIVE` / `PAUSED` deployment of the organization (optionally one account) `STOPPED`, epoch + 1, sessions as above; permission `bot.emergency_stop`. Retire: sessions stopped first, then `RETIRED`, epoch + 1. Each needs a typed confirmation matching the current state (live-session or deployment count; the bot key to retire; the phrase `EMERGENCY STOP`).

**Not in 08C:** suppressing `QUEUED` BOT requests (`QUEUED -> HELD`) needs the BOT columns of migration 0008 and belongs to 08D, together with the concurrency correction tracked below (now owner-reported CLOSED for 08D). No BOT request can exist before 08D (`requests_suppressed` is always 0 at the 08C checkpoint).

### 8. Privacy redaction (V3.2 K.11)

`bot_session_redaction_after()` returns `interval '30 days'`; `redact_expired_bot_sessions(org, limit)` (limit 1-10000, organization required) clears `variables`, `awaiting`, `awaiting_token`, `last_consumed_token` and sets `redacted_at` for terminal sessions of that organization past the period, in one statement with `FOR UPDATE SKIP LOCKED`; it takes no other lock, allocates no sequence and writes no event. The guard admits exactly that shape (NULL-safe: `IS DISTINCT FROM '{}'::jsonb`, `IS NOT NULL`), only after the period, never on a live row, and nothing after redaction. Nothing calls the function yet (pinned by a boundary test); the scheduled job is 08F.

### 9. Services, auditing and the operator command line

`src/modules/bot-control` (a separate module; `src/modules/bots` stays pure and now refuses subdirectories) provides create bot, update / read / validate draft, publish, list / read versions, activate, change version, pause, resume, Stop Active Sessions, Emergency Stop and Retire, plus listings and the live-session count preview. Auditing is operation-appropriate: deployment operations write `bot_deployment_events` (actor, versions, statuses, epoch, counts) and session hand-overs write `bot_session_events`; drafts and publications are recorded durably on their own rows (`draft_updated_by_membership_id`, `draft_revision`, `draft_updated_at`; `published_by_membership_id`, `published_at`, `config_sha256`), never as deployment events; every committed change also logs one `bots.admin_action` line with ids, codes and counts only. `scripts/bots-admin.ts` (`npm run bots:admin`) acts as a real member resolved from the database (`--organization`, `--actor <email>`); the services re-check that member under the locks. It prints one JSON document, performs state changes as dry runs (executed, then rolled back) unless `--apply`, and refuses destructive controls without a matching confirmation. No HTTP route or page uses the module.

### 10. Test-harness safety

`createTestDatabase` refuses unless `TEST_DATABASE_ADMIN_URL` is explicitly set (no default; `DATABASE_URL` and `.env.local` are never used) to a plain `postgres:`/`postgresql:` URL with an explicit user, a local TCP host (`localhost`, `127.0.0.1`, `[::1]`), the maintenance database `postgres` (never `al_ict_whatsapp`) and no query string, fragment or whitespace (the installed `pg-connection-string` lets query parameters override host, port and database, and accepts `socket:` and socket paths). pg's own `ConnectionParameters` must then resolve both the string and the explicit config built from it to that same host, port, database and user (so `PG*` environment variables cannot redirect it), and the pools are created from that explicit config, never from a connection string. All of this runs before any client or pool exists. The harness then creates and drops only the name it generated, matching `^al_ict_(test|e2e)_[0-9a-f]{12}$`, re-checked immediately before `DROP DATABASE`. Phase 08C tests use `al_ict_test_*` only.

## Development defaults (owner-approved through the plan review)

1. A `RETIRED` deployment releases its bot and priority slots (partial uniques `WHERE status <> 'RETIRED'`; an amendment of K.3) and stays immutable.
2. Permissions: `bot.read` ADMIN and STAFF; `bot.edit`, `bot.publish` and `bot.emergency_stop` ADMIN only (STAFF escalate operationally through an ADMIN); VIEWER none.
3. Session sensitive fields are redacted 30 days after `ended_at`: a development policy, not a legal conclusion; changing it is a reviewed migration replacing `bot_session_redaction_after()`.
4. Administration is command-line only in 08C, acting as a real, re-validated member, every change audited.
5. The database stamps `started_at` and `ended_at` (and deployment and version times).
6. **Owner decision D-1 (2026-10-26, Phase 08F-1):** terminal `bot_triggers` rows (`PROCESSED`, `IGNORED`, `DEAD`) are deleted 14 days after `processed_at` (at or before the cutoff), only by the bounded `bots:retention` job; `PENDING`, claimed, too-recent and locked rows never. The period is `TRIGGER_RETENTION_DAYS` in `src/db/ops/bot-trigger-retention.ts` and a floor inside the delete statement; changing it is a reviewed code change. The 30-day session redaction (item 3) is unchanged. This decision authorizes no production run or schedule.
