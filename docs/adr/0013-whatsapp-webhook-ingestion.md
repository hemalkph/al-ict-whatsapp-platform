# ADR 0013: WhatsApp webhook ingestion

Status: Accepted for Phase 04. Checkpoint 1 (G0 evidence, fixtures, schema, migration 0002) is done and checkpoint 2 validated migration 0002 against real PostgreSQL 17.11 on disposable databases (it has never been applied to the developer database). Checkpoint 3 adds the queue and worker core (no domain handlers). Checkpoint 4A adds contact identity resolution for normal inbound messages. Checkpoint 4B adds the inbound MESSAGE handler and checkpoint 4C the STATUS handler. Checkpoint 5A adds a standalone worker that runs exactly those two handlers; it is disabled unless explicitly enabled and is not deployed anywhere. The remaining domain handlers come in later checkpoints. Supersedes nothing; extends [ADR 0006](0006-webhook-inbox-no-redis.md). Evidence: [WHATSAPP_G0_EVIDENCE.md](../WHATSAPP_G0_EVIDENCE.md).

## Context

Meta's WhatsApp Cloud API delivers inbound messages and statuses to one HTTPS webhook per app. Delivery is at-least-once with no ordering guarantee and retries for up to 7 days (WhatsApp pages; the generic Graph page says 36 hours). Payloads reach 3 MB. Since April 2026 users may be identified only by a business-scoped user ID (BSUID); the phone-based `wa_id` and the message `from` can be absent. The Phase 02 tables (`webhook_requests`, `webhook_events`, `contacts`, ...) predate these facts.

## Decisions

### 1. The signature rule (non-negotiable)

```
HMAC-SHA256( META_APP_SECRET, exact received HTTP request-body bytes )
```

compared in constant time with the hex digest after `sha256=` in `X-Hub-Signature-256`. **This is the only accepted signature.** No alternate representation is ever accepted: not `JSON.stringify`, not decoded-and-re-encoded JSON, not Unicode normalization, not Unicode re-escaping, not canonical JSON, and there is no fallback "second candidate". The verifier will take a `Uint8Array` only (no string or object overload), so a transformed representation cannot reach it by construction.

Meta's Messenger Platform page says its signature is computed over an "escaped unicode version of the payload" and that hashing decoded bytes gives a different result. That sentence is recorded in the evidence file; it does **not** open an alternate path. If a real Sinhala/Tamil delivery ever fails on its exact received bytes, that is a **transport/framework investigation** (something between Meta and our handler altered the body: a proxy, a CDN, a framework that decoded and re-encoded), never a reason to weaken verification. The optional live smoke only _confirms_ the raw-byte assumption.

Verification happens **before** parsing or persisting anything; invalid signatures are rejected with no database write (invalid-signature telemetry is a log line, not a table, so forged requests cannot cause writes).

### 2. Raw request storage

`webhook_requests.raw_payload jsonb` is replaced by `raw_body bytea NOT NULL` holding the exact bytes. jsonb is not the wire body (it reorders keys, drops duplicate keys, normalizes numbers) and it rejects `\u0000`, so it can neither re-verify a signature nor replay a delivery, and one NUL would fail the insert and poison Meta's retries. `payload_sha256` is kept and now means the lowercase-hex SHA-256 of the exact bytes (CHECK `^[0-9a-f]{64}$`). Parsed content lives per item in `webhook_events.payload`; there is no second full parsed copy at request level. Raw bodies contain personal data (numbers, names, message text): never logged, never returned by an API, and a retention policy is a pre-production requirement ([PRE_PRODUCTION_BLOCKERS.md](../PRE_PRODUCTION_BLOCKERS.md)).

### 3. Signed-but-malformed deliveries: ACK 200 after durable storage

| Situation                                                                       | Response | Stored                                            |
| ------------------------------------------------------------------------------- | -------- | ------------------------------------------------- |
| Invalid signature                                                               | 403      | nothing                                           |
| Body above the cap                                                              | 413      | nothing                                           |
| Valid signature, invalid UTF-8 / invalid JSON                                   | **200**  | request row, `ingest_status = UNPARSEABLE` + code |
| Valid signature, JSON that is not the expected envelope                         | 200      | `UNSUPPORTED_SHAPE` + code                        |
| Valid signature, deterministic event-persistence failure (SQLSTATE class 22/23) | 200      | request row only, `EVENTS_REJECTED` + code        |
| Database unavailable, transient error, or the bytes cannot be durably stored    | **500**  | nothing (Meta retries)                            |

Returning 400 for signed-but-invalid JSON was rejected: Meta retries the same bytes, so a syntactically invalid body can never become valid by retrying and days of retries would only form a poison loop. Because the exact bytes are kept and the failure is recorded, nothing is lost and a future replay tool (needs `webhook.manage`) can re-run the parser after a fix. UTF-8 is decoded with a fatal decoder (invalid bytes are rejected, never replaced). `ingest_error_code` is a short fixed code (1 to 64 characters, `NULL` exactly when `ACCEPTED`), never exception text.

### 4. Request and event model

`webhook_requests` = one HTTP delivery. `webhook_events` = one item extracted from it: a message, a status, an `IDENTITY` change, or an ignored `OTHER` change. Idempotency keys are namespaced, versioned and always scoped by `phone_number_id`: `wa:msg:v1:{phone_number_id}:{wamid}`, `wa:status:v1:{phone_number_id}:{wamid}:{status}:{timestamp}`, `wa:other:v1:{scope}:{sha256(RFC 8785 canonical JSON)}`. wamids are opaque strings, never parsed. The two-level model, the global unique idempotency key and the `SKIP LOCKED` queue are unchanged.

### 5. Routing and account states

Events route by `metadata.phone_number_id` to `whatsapp_accounts.phone_number_id` (never the display number), with `entry.id` cross-checked against `waba_id` (subject to a live confirmation). Existing statuses are used; no new status is added.

| Account state at ingest   | Event status          | Routing columns | Reason             | Released                                                                                    |
| ------------------------- | --------------------- | --------------- | ------------------ | ------------------------------------------------------------------------------------------- |
| ACTIVE                    | `PENDING`             | set             |                    | normal processing                                                                           |
| PENDING (being set up)    | `UNROUTABLE` (a hold) | set             | `account_pending`  | automatically when THAT account is activated (events younger than 30 days)                  |
| unknown `phone_number_id` | `UNROUTABLE`          | NULL            | `unknown_account`  | explicit operator decision per event, naming a verified target account; never automatic     |
| WABA mismatch             | `UNROUTABLE`          | NULL            | `waba_mismatch`    | explicit operator decision per event, only once phone number AND WABA agree with the target |
| DISABLED                  | `IGNORED`             | set             | `account_disabled` | explicit operator requeue only; re-enabling an account releases nothing automatically       |
| archived                  | `IGNORED`             | set             | `account_archived` | explicit operator requeue only                                                              |

**Tenant provenance is stronger than current phone-number ownership.** Once ingest matched an account (consistent `phone_number_id` and WABA), the event keeps that `organization_id`/`whatsapp_account_id` for life, including while it is held; a hold never erases it and nothing ever re-derives it from today's owner of the number. An event that was never matched (`unknown_account`, `waba_mismatch`) has no proven owner and acquires routing only through an explicit, verified operator decision. An old payload therefore cannot become another organization's data because a phone number was later configured under it. An account changing state between ingest and processing moves the event the same way (PENDING back to an `UNROUTABLE` hold **keeping** its routing; DISABLED/archived to `IGNORED`) and **does not count as a processing attempt**. Release is two distinct operations: routed events are released only against their own account, unrouted ones only by an explicit per-event decision (see the checkpoint 3 notes). Nothing is silently lost: held and ignored rows keep their payload until retention (which must exempt held events). The checkpoint-1 schema needs no new column for any of this.

### 6. Provider timestamps are facts

`messages.occurred_at` (and status `occurred_at`) store the provider timestamp whenever it is a positive integer within the JavaScript `Date` range; nothing is clamped or rewritten to protect ordering. A separate **effective activity time**, `LEAST(provider_ts, event.received_at + 5 min)`, is the only value used for derived state: `conversations.last_message_at`, `last_inbound_at` (existing monotonic `GREATEST` operation), the reopen check, and **every future customer-service-window calculation, which must read `conversations.last_inbound_at` and never `messages.occurred_at`**. A future-dated message therefore cannot extend the window by more than 5 minutes or reorder the inbox while its history stays untouched. Anomalies (`timestamp_future`, `timestamp_stale`) are logged with the delta and a reason code, no personal data. Known limitation: the per-conversation message timeline sorts by `occurred_at`, so an absurd provider timestamp sorts oddly until time catches up.

### 7. BSUID identity and history

- `contacts.wa_id` becomes nullable (a BSUID-only user has no phone-based id; `UNIQUE (organization_id, wa_id)` is unchanged and still rejects duplicates among non-NULL values) and `contacts.username` is added (untrusted display text). There is **no `contacts.bsuid`**.
- New table **`contact_bsuids`** is the single source of truth for BSUID ownership and history: `UNIQUE (organization_id, bsuid)` (a BSUID can never belong to two contacts, even when retired), a composite organization-aware FK to `contacts`, `retired_at` (NULL = not known to be superseded), timestamps with ordering CHECKs, an index for contact lookup (newest seen first). Meta regenerates the BSUID when a user changes phone number and redelivers webhooks for days in no guaranteed order, so a late event carrying the old BSUID must resolve to the existing contact instead of creating a duplicate; a single "current BSUID" column cannot do that. Phone numbers are **not** aliased: they are recycled between people, BSUIDs are unique per portfolio-user pair.
- **No "one current alias per contact" unique index.** Meta documents regeneration but not whether the old BSUID stops being valid at once or whether two can coexist (G0 item H2). The database does not assert what Meta does not document. The application keeps at most one non-retired alias per contact and picks the newest `last_seen_at` if it ever sees more. A later migration can add the index once evidence exists.
- **Provenance:** `source_webhook_event_id` references `webhook_events(id)` `ON DELETE SET NULL` (single column), so it can never block pruning old events. Tenant ownership comes from `organization_id` + `contact_id`, not from this pointer. Note: the Phase 02 provenance FKs on `messages.source_webhook_event_id` and `message_status_events.webhook_event_id` are composite `NO ACTION` and **do** block pruning until a retention job nulls them first (their documented design); that is unchanged, and the retention job must handle it.
- Contact matching inside a delivery is explicit: primary `messages[].from_user_id <-> contacts[].user_id`, fallback `messages[].from <-> contacts[].wa_id`; never `contacts[0]`, never array position (H3: no official example has more than one sender per `value`; the multi-sender fixture is synthetic).

### 8. Identity changes: handler design STOPPED (G0 item H1)

Official pages contradict each other about how identity changes are delivered ([evidence](../WHATSAPP_G0_EVIDENCE.md)): the BSUID page documents a system message carrying only the **new** BSUID plus a separately subscribable `user_id_update` field carrying `previous`/`current`; the webhooks overview field list omits `user_id_update`; a legacy page documents `user_changed_number` with phone numbers. An earlier working assumption (a `system.previous_user_id` property) came from a search summarizer and is **not supported by any official text**; it is discarded. Decided now: `system.body` is never parsed; no handler may depend on an undocumented field; the old BSUID is available only from a structured `previous` field; conflicting mappings fail closed (never silently merged). **Not decided until H1 is closed** (a look at the real App Dashboard's field list): which delivery will occur, the exact `system.type` values, and any automatic `wa_id` mutation. Policy by documented subtype, for now: `user_changed_user_id`, `user_changed_number` and `user_id_update` each have **insufficient evidence, so no automatic `wa_id` mutation is allowed** (the earlier "clear or replace `wa_id`" idea is withdrawn). `wa_id` is only ever filled by ordinary message handling when empty and unused. An identity-change item is never an ordinary chat message (no message row, no conversation activity); its raw payload stays preserved for audit and replay. Other system messages are stored as `SYSTEM` only when the contact and conversation already exist, and never advance activity.

### 9. Business portfolio invariant

BSUIDs are scoped to a **Meta Business Portfolio**, not to a phone number, and the documentation does not equate a portfolio with a WABA. `UNIQUE (organization_id, bsuid)` is therefore correct only while **one application organization = one Meta Business Portfolio**. This is an **onboarding invariant**: the account-onboarding operator tool will require explicit confirmation and the runbook states it (it cannot be verified without an authenticated Graph call, which Phase 04 does not make). If one organization ever contains accounts from several portfolios, the required schema change is: add `business_portfolio_id` to `whatsapp_accounts` and `contact_bsuids`, scope uniqueness to `(organization_id, business_portfolio_id, bsuid)`, take the portfolio from the receiving account during resolution, and revisit parent BSUIDs. WABA id is never substituted for the portfolio id.

### 10. Media attachments

A `message_attachments` row with `storage_status = PENDING` means **provider media exists but has not been fetched yet**. No downloader exists or consumes these rows in Phase 04; `message_attachments_pending_idx` is reserved for the future downloader. No Phase 04 health check treats PENDING attachments as a failing queue: queue health looks only at `webhook_events`. Meta media ids from webhooks expire after 7 days and media URLs after 5 minutes (verified), so the downloader must fetch promptly and must handle `EXPIRED`. The media `url` in the webhook is not persisted outside the retained event payload.

### 11. Worker semantics (decided now, implemented later)

`MAX_ATTEMPTS = 8` handler runs per event, crashed runs included. `attempts` counts claims (the existing claim operation increments it on every claim, including lease reclaim): the first claim makes it 1; after any claim, `attempts > 8` marks the event `DEAD` **without running the handler**; a transient failure with `attempts >= 8` marks it `DEAD` (no further retry), otherwise `FAILED` with `next_attempt_at = now + delay`. A permanent error is `DEAD` after one run. Backoff `delay(n) = min(30 s * 2^(n-1), 1 h)` with plus or minus 20 % uniform jitter gives the nominal gaps **30 s, 1 m, 2 m, 4 m, 8 m, 16 m, 32 m** before runs 2 to 8 (3,810 s = 63 m 30 s nominal in total; 50 m 48 s to 76 m 12 s with jitter). Lease 120 s; per-event wall clock 60 s and `statement_timeout` 15 s stay below the lease. Completion and failure updates are fenced on `status = 'PROCESSING' AND locked_by = me`.

### 12. Graph version

Recorded only (observation, 2026-10-04): v26.0 (2026-07-29, latest), v25.0 (2026-02-18, expires 2028-07-29), v24.0 (2025-10-08), v23.0 (2025-05-29). Inbound webhooks make no Graph call and require no version choice from us; the outbound version is decided in the outbound phase.

## Migration 0002 deployment precondition (validated)

`0002` runs `ALTER TABLE webhook_requests ADD COLUMN raw_body bytea NOT NULL` **before** `DROP COLUMN raw_payload`, with no default and **no backfill**. That is correct only while `webhook_requests` is empty, so **0002 must be deployed before any real webhook data exists**. No runtime code writes the table yet, so every existing database satisfies this today; once the webhook route ships and a delivery has been stored, the precondition is permanently gone and a different migration would be needed.

- Deliberately not done: filling `raw_body` from `raw_payload`. Serializing the jsonb would fabricate bytes that were never on the wire, could never re-verify a signature, and would make a stored hash look authoritative.
- Proven by `src/db/__tests__/migration-0002-precondition.db.test.ts` with the real drizzle migrator: on a pre-0002 database with an empty `webhook_requests` the migration applies (22 to 23 tables); with one existing row it fails with SQLSTATE `23502` (`column "raw_body" of relation "webhook_requests" contains null values`, statement 4 of 17), and **nothing is half-applied** (0002 is not recorded, `contacts.wa_id` is still NOT NULL, `contact_bsuids` does not exist, the original row and its jsonb are untouched); and once the table is empty by an operator decision the same migration applies. The migrator runs the pending migrations in one transaction, which is what makes the failure safe.
- If real or user data could already be in `webhook_requests` anywhere, **stop**: do not run 0002 and do not edit it automatically; decide the data's fate first (it would have to be exported as evidence, not converted).
- Run order for a deployment: apply `0002` first, then deploy the version that contains the webhook route.

## Implementation notes (checkpoint 2: pure core and HTTP ingress)

Implemented in `src/modules/whatsapp/` behind a two-function public API; the route imports only that. Decisions taken while implementing:

- **Exact bytes only.** `verifyWebhookSignature(body: Uint8Array, header, secret)` has no string or object overload (checked by the compiler in a test), computes exactly one HMAC, and a static test asserts it contains no JSON, normalization, escaping or canonical form. The handler reads `request.body` as bytes through a bounded reader (4 MiB, streamed count; `Content-Length` only as a hint); it never calls `request.json()` or `request.text()`. UTF-8 is decoded with a fatal decoder that keeps a BOM.
- **Oversize refusals close the connection.** A 413 carries `Connection: close`. Found with a stalling raw client and an E2E run: after answering 413 the server otherwise held the request open until the client left. Covered by a handler test and a real-server E2E test.
- **Deterministic versus transient** is decided by SQLSTATE (22, 23 and 54 deterministic; also `RangeError` from very deep nesting), inside a savepoint so a deterministic child failure leaves the request row (`EVENTS_REJECTED`, `event_insert_data_error`) and no children, while infrastructure errors roll everything back and answer 500. A normalizer failure (a pure function of the bytes) is stored as `EVENTS_REJECTED` / `normalize_failed`.
- **System messages are not interpreted** (H1 unresolved): every `system` message becomes an `IGNORED` `OTHER` event (`system_message_pending_h1`) with the raw item preserved. No `IDENTITY` event is ever emitted. `user_id_update` is just an unsupported field.
- **Canonical JSON** (`src/shared/canonical-json.ts`) is the RFC 8785 Appendix A sample canonicalizer (JSON.stringify for primitives, UTF-16 code-unit key order), refusing non-finite numbers; tested against the official section 3.2.3 example and every Appendix B number row. It is imported only by the idempotency-key module.
- **Event payload** (`webhook_events.payload`): `{v:1, wabaId, field, metadata, contact, pairing, message}` for messages, `{..., status}` for statuses, `{..., element}` for other items, all NUL-stripped and well-formed.
- **No `after()`, worker, timer or Meta call** exists in the ingest path (a static test scans for them).

## Implementation notes (checkpoint 3: queue and worker core)

Infrastructure only: **no contact, conversation, message, status or identity handler, no Meta call, no UI, no migration** (the checkpoint-1 columns `status, attempts, next_attempt_at, locked_at, locked_by, last_error, processed_at` were sufficient). Code: `src/db/ops/webhook-queue.ts` (claim and the fenced transitions), `src/modules/whatsapp/queue/` (`policy`, `errors`, `process`, `requeue`, `stats`, `timeout`) and `src/modules/whatsapp/envelope.ts`.

- **Claim.** One committed statement: `SELECT ... FOR UPDATE SKIP LOCKED` over due `PENDING`/`FAILED` rows and `PROCESSING` rows whose lease expired (`locked_at` older than 120 s, or missing), ordered by `(received_at, id)`, then `UPDATE` to `PROCESSING` with a fresh `locked_by`, `locked_at = now()` and `attempts + 1`. `PROCESSED`, `DEAD`, `UNROUTABLE` and `IGNORED` are never claimed. The claim can be limited to event types, and the worker only claims types that have a registered handler.
- **Attempts = claims.** At most `MAX_ATTEMPTS = 8` handler runs per event. Claim 1 sets `attempts = 1`. A claim that finds `attempts > 8` (only possible after a run that crashed on attempt 8 and was then reclaimed) marks the event `DEAD` (`max_attempts_exhausted`) **without invoking the handler**. A transient failure on attempt 8 is `DEAD` at once (`exhausted_<code>`); attempts 1-7 become `FAILED` with `next_attempt_at = now + delay`. A permanent failure is `DEAD` after one run.
- **Backoff.** After attempts 1-7: 30 s, 1 m, 2 m, 4 m, 8 m, 16 m, 32 m (a fixed table, sum 3,810 s), with uniform +/-20 % jitter. The clock and the random source are injected, so tests never sleep.
- **Lease and budgets.** Lease 120 s, no heartbeat. Per-event wall-clock budget 60 s (the handler's `AbortSignal` fires, the transaction cannot commit afterwards) and `statement_timeout` 15 s set with `set_config(..., true)` inside the handler's transaction. The batch refuses a handler budget that is not shorter than the lease.
- **Fencing.** Every transition is `UPDATE ... WHERE id = ? AND status = 'PROCESSING' AND locked_by = ?`; zero rows means the lease was lost and nothing else is written. `locked_by` is a fresh UUID **per claim** (not per process), so even a stale run of the same process cannot match a newer claim.
- **Handler contract.** `handler(tx, event, context)`: `tx` is the same transaction that performs the fenced `PROCESSED` update, so domain writes and the completion commit or roll back together; losing the fence throws and rolls the handler's writes back. A handler throws `PermanentWebhookError(code)` (a fixed lowercase code; anything else is replaced by `permanent_error`) when retrying cannot help. Every other throw is transient, **including PostgreSQL constraint errors**: the generic worker never decides that a constraint violation is permanent. `last_error` only ever holds a code from `classifyFailure` (`unexpected_error`, `pg_<sqlstate>`, `handler_timeout`, ...), never a message, payload text, phone number, BSUID or token.
- **No worker is started and none can silently run.** The core is `processWebhookBatch(db, { handlers, ... })` with a **required, explicit** registry; there is no default registry and no no-op handler, and an event type without a handler is never claimed (it stays `PENDING`). No `whatsapp:worker` command exists yet (design "option A"): it arrives with the domain handlers. A static test fails if a worker/queue script, an app route or the public API ever references the core before then.
- **Batching.** Defaults: batch size 20, handler concurrency 2 (bounds 1-100 and 1-8). Each lane claims **one** event immediately before running it, so a lease never ticks while an event waits for a free lane (claiming 20 at once behind two 60 s handlers would outlive the 120 s lease). Each event has its own transaction and outcome; a poison event cannot roll back another. The returned summary holds counts only (`claimed, processed, failed, dead, held, ignored, leaseLost, unrecorded`; `unrecorded` = the outcome could not be written, the lease expiry recovers the event).
- **Account recheck before the handler** (same table as ingest): archived -> `IGNORED account_archived`, DISABLED -> `IGNORED account_disabled` (routing kept), PENDING -> `UNROUTABLE account_pending` (routing KEPT: holds never erase tenant provenance). These are **not** handler runs: the claim's increment is undone (`attempts` returns to its pre-claim value). A missing routing is `DEAD missing_routing`.
- **Release of held events (two operations, tenant provenance first).** Nothing ever changes an event's organization or account once ingest set them, and a phone number configured under some organization today is never, by itself, a reason to give it an old payload.
  - `requeueRoutedHeldEvents(tx, { whatsappAccountId, reasons, receivedAfter })` is for events ingest already routed (`account_pending`, `account_disabled`, `account_archived`). It loads that exact account `FOR SHARE` and requires it to exist, to be `ACTIVE` and not archived. It selects only events whose own `organization_id` and `whatsapp_account_id` equal the account's and whose stored `phone_number_id` and WABA equal the account's. It refuses the whole call (`organization_mismatch`) if any held event of that account names a different organization than the account row (ownership drift is never repaired by requeue). It never writes routing columns; it sets `PENDING`, `attempts = 0`, due now, clears the lease and `last_error`.
  - `requeueUnroutedEvent(tx, { webhookEventId, targetWhatsappAccountId, receivedAfter })` is for ONE `unknown_account` or `waba_mismatch` event (routing NULL). An operator names the target; the operation independently verifies that the event is still an unrouted hold, the target exists, is `ACTIVE` and not archived, the event's stored `phone_number_id` is the target's, the WABA equals the target's (required for `waba_mismatch`; for `unknown_account` it must match whenever the event carries one), and the event is no older than the operator-confirmed `receivedAfter`. Only then does the event take the target's organization and account. An event that already has routing is refused here, so it can never be moved to another organization or account. Refusals return a fixed code (`event_not_unrouted`, `account_not_active`, `phone_number_mismatch`, `waba_mismatch`, `event_too_old`, ...).
  - `requeueOnAccountActivation(tx, { whatsappAccountId })` releases ONLY `account_pending` events already routed to exactly that account and received within 30 days (a domain constant). Older ones stay held and are counted (`staleHeld`). `unknown_account`, `waba_mismatch`, `account_disabled` and `account_archived` are never released automatically; disabled/archived history is released only by an explicit routed call against its own account.
  - No function accepts an organization id. The phone number and WABA are read from the stored envelope only through `envelope.ts` (JS and SQL readers, tested against what the real normalizer stored), because unrouted events have NULL routing columns.
- **Account ownership is immutable in this phase.** No application, script or Phase 04 operation updates `whatsapp_accounts` (a static test scans production sources and scripts for it), and requeue never writes the account row. The composite foreign key `webhook_events (organization_id, whatsapp_account_id) -> whatsapp_accounts (organization_id, id)` is `ON UPDATE NO ACTION`, so PostgreSQL itself refuses to change `organization_id` of an account that has webhook history (tested); the defense in depth is that requeue refuses if ownership ever drifted anyway (tested by bypassing the FK in a scratch database). Moving a number to another organization is a new onboarding workflow (a new account), not an `UPDATE`. No trigger was added. An account with no history could still be re-pointed by direct SQL until a trigger or an operator workflow forbids it; that belongs to the onboarding checkpoint.
- **Observability.** `readQueueStats` returns counts per status, the age of the oldest due `PENDING`/`FAILED` event and the number of expired leases; no content is selected. Worker logs use the same fixed-field emitter (`webhook.event_{processed,failed,dead,held,ignored,lease_lost,unrecorded}`, `webhook.batch_completed`; fields: internal event/organization/account ids, event type, attempt, duration, outcome, reason code, counts); `dead` logs at error level. Payloads are never logged.
- **Not done here:** domain handlers, the worker command, the activation operation and the operator requeue commands (the functions exist; nothing calls them), the queue-status command, retention. The ingest path imports nothing from the queue (static test).

## Implementation notes (checkpoint 4A: contact identity resolution for normal inbound messages)

`src/modules/whatsapp/identity/` (`resolve.ts`, `profile.ts`) plus `time.ts`. **Not wired to anything**: no message handler, no conversation, no status handler, no identity-change handler, no worker command, no Meta call, no UI, no migration, no new table. It reuses `contacts` and `contact_bsuids`.

- **API.** `resolveInboundContact(tx, event, { observedAt })` returns `{ contactId, created, conflicts }`. `event` is the trusted queue event (`id`, `eventType`, `organizationId`, `whatsappAccountId`, `receivedAt`, `payload`). The organization is `event.organizationId` only (set by ingest from our own `whatsapp_accounts` row); nothing in the payload can choose a tenant (tested with a payload that names another organization). Sender identity is read from the stored envelope by `readInboundIdentity`: `message.from_user_id` (BSUID), `message.from` (phone-based id, opaque), and the `contact` element only when it provably belongs to this message (paired by the normalizer and consistent with the message's own identifiers; never `contacts[0]`). Parent BSUIDs, system messages, `user_id_update` and any previous/old identifier are never read (a static test forbids it). Only `MESSAGE` events are accepted. A message with no usable identifier, or an unusable one (empty, over 255 characters, control characters), fails with a fixed `PermanentWebhookError` code (`missing_sender_identity`, `invalid_sender_identity`, `invalid_event_payload`, `not_a_message_event`).
- **Transaction contract.** It runs inside the caller's (the worker's) transaction and opens none: no `.transaction()`, no savepoint, no connection of its own (static test). It refuses a plain connection (the advisory locks would be released at the end of each statement) and any isolation level other than READ COMMITTED (lock-then-read needs fresh snapshots). If the worker's completion fails, the contact and alias roll back with the event (tested, including a failure at COMMIT).
- **Principle (revised after review).** A phone number alone is **not** proof of identity continuity: numbers are recycled between people. BSUID aliases are authoritative, and a duplicate contact is preferable to an incorrect identity merge. Automatic legacy-phone-to-BSUID linking is therefore **disabled**; reconciling duplicates is a manual operation that is deferred.
- **Resolution.** (1) A known BSUID, current **or retired**, always resolves to the alias's contact. A retired alias row is not touched at all: not reactivated, not promoted, not even its last-seen. (2) An unseen BSUID whose phone no contact owns creates a contact (phone as `wa_id`) and its alias in one transaction. (3) An unseen BSUID whose phone is **owned by any existing contact** gets its **own BSUID-only contact without the phone**; nothing is linked, merged or moved. The reported reason is `legacy_phone_ownership_unverified` when the owner is a legacy phone-only contact (no aliases) and `phone_held_by_bsuid_contact` when the owner already has an alias, current or retired. The existing contact is left byte-for-byte unchanged. (4) A **phone-only** message (no BSUID) is a legacy-shaped or incomplete observation, since Meta's documented inbound format carries a BSUID. If the phone belongs to a contact with **no** aliases, that contact resolves it (inherently uncertain; the contact is never BSUID-verified and no BSUID is invented). If the phone belongs to a contact **with** aliases, it is **refused** with the fixed permanent code `phone_only_identity_ambiguous` (the event becomes `DEAD`) and nothing is modified or created. If the phone is unknown, a phone-only contact is created and is likewise not BSUID-verified. Names and profile data are never used to guess identity.
- **Phone rules.** `wa_id` is only filled when empty and unowned, never rewritten. For a known BSUID: a phone owned by a different contact reports `phone_owned_by_other_contact` and nothing moves; a phone different from the contact's own reports `phone_differs_from_contact` and the stored phone is kept. There is no automatic `wa_id` change from any identity-change assumption.
- **Alias ownership is immutable.** Aliases are only inserted (`ON CONFLICT DO NOTHING`), or have their `first/last_seen_at` widened for a current alias. No statement updates `contact_id`, `bsuid` or `retired_at`, there is no `ON CONFLICT DO UPDATE`, and no alias is deleted (static tests). Tests run long sequences of conflicting messages and assert every alias keeps its owner. The schema would permit an in-tenant `UPDATE contact_id`; no trigger was added, as decided.
- **Concurrency.** Before reading, the resolver takes `pg_advisory_xact_lock(hashtextextended(key, 0))` for each identifier of the message (`wa-identity:{organization}:bsuid:{value}` and `...:wa:{value}`), de-duplicated and **sorted**, so every transaction takes them in the same order. A second transaction for the same identity waits for the first to commit and then sees its rows. The unique constraints are the second, independent defense: contact and alias inserts use `ON CONFLICT DO NOTHING`; a lost race removes the contact just created and re-resolves (bounded), otherwise the worker retries transiently. Tested with repeated rounds of simultaneous first messages (same BSUID, BSUID-only racing BSUID+phone, several BSUIDs on one phone, a legacy contact racing two BSUIDs, a retired alias racing a new BSUID, two organizations).
- **Profile.** Name and username come only from the contact element paired with this message. They are untrusted display text: NUL, control and bidi controls removed, whitespace collapsed, NFC, at most 200 (name) or 100 (username) code points; zero-width joiners are kept because Sinhala and Tamil need them. They are never identity. They are replaced only by an event at least as new as the newest already seen and never by nothing, so a delayed older event cannot overwrite newer data and an absent profile cannot erase one.
- **Time.** `first_seen_at` only decreases and `last_seen_at` only increases. The caller passes the provider time; the resolver caps it at receipt + 5 minutes (`effectiveActivityTime`), so a future-dated message cannot freeze profile updates or last-seen.
- **New contacts** carry the organization, identity, seen window and the default consent cache `UNKNOWN`. Nothing creates a lead, student, conversation, message, consent event or tag (every such table is asserted empty after every test).
- **Visibility.** `webhook.contact_identity_conflict` (reason codes: `phone_owned_by_other_contact`, `phone_differs_from_contact`, `phone_held_by_bsuid_contact`, `legacy_phone_ownership_unverified`, `phone_only_identity_ambiguous`) uses the fixed-field emitter with internal ids only; no phone, BSUID, profile text or message text is ever logged (tested). A retried event may log again.

**Residual risks and limitations (documented, not solved here)**

1. **Duplicate contacts instead of merges.** A customer who was known only by phone and now arrives with a BSUID becomes a second contact, and the legacy contact keeps its history. This is deliberate (decision above). Manual reconciliation (an operator-confirmed merge with an audit trail) is deferred; until then those duplicates are visible through the conflict log and the `legacy_phone_ownership_unverified` reason.
2. **Phone-only observations stay inherently uncertain.** A phone-only message for a contact without a BSUID resolves by phone, which cannot exclude a recycled number; such a contact is never BSUID-verified. The same message for a BSUID-established contact is refused rather than guessed.
3. Duplicate BSUID contacts and duplicate aliases are prevented by advisory locks and the unique constraints (mutation-tested); there is deliberately no "one alias per contact" constraint (G0 item H2).
4. A user who changes number and gets a new BSUID before any identity-change handling exists appears as a new contact. Linking them is the unresolved H1 work and is not attempted.
5. A removed username or name cannot be told from an absent one, so it is kept.
6. An archived contact that sends a message stays archived; whether to unarchive is the message handler's decision.
7. Parent BSUIDs are ignored.

## Implementation notes (checkpoint 4B: inbound MESSAGE processing)

`src/modules/whatsapp/inbound/` (`message-map.ts`, `handler.ts`) and `src/db/ops/inbound-message.ts`. **No migration, no new table.** The handler is `handleInboundMessage(tx, event, context)`, a normal queue handler (`WebhookHandler`); the registry `inboundMessageHandlers = { MESSAGE }` is passed explicitly by tests. **Nothing starts a worker** (no `whatsapp:worker`, no default registry). STATUS, IDENTITY and OTHER events stay unclaimed. No Meta call, no outbound message, no bot, no media download, no lead, student or consent is created.

- **Order of operations (this order is pinned by a static test).** Map and validate the stored envelope; verify the routed account is ACTIVE for this organization; take a transaction-scoped advisory lock on `(organization, account, wamid)`; look for the message and, if found, do **nothing at all**; then, inside a savepoint of the worker's own transaction: resolve the contact (4A, unchanged), get or create the conversation, look up the reply parent, insert the message, and only now advance activity / reopen, add the attachment, back-resolve waiting replies and write the attribution. The handler never touches the event row: it returns or throws, and only the queue's fenced update sets PROCESSED.
- **Duplicates.** A duplicate creates no contact, alias, conversation, activity change, reopen, attachment, link or attribution, and does not even touch the contact's `updated_at` (tested by comparing every row before and after a replay, for a replay of the same event, a second event with the same wamid, a duplicate after the conversation was resolved, and two workers racing). Three layers: the per-message advisory lock (two workers serialize, the second sees the committed message), the early existence check, and `INSERT ... ON CONFLICT DO NOTHING` on the existing unique index `(organization_id, whatsapp_account_id, wamid)`; if that insert still reports a conflict (a writer that does not take the lock), the savepoint rolls every provisional write back and the event completes as a duplicate. The unique index is the final protection.
- **Conversation.** One per `(organization, account, contact)`, created with `ON CONFLICT DO NOTHING` plus a re-read, so concurrent first messages cannot duplicate it, and an existing one is returned untouched. A contact messaging two business numbers gets two conversations; organizations never share one. New: OPEN. Existing OPEN or PENDING: status kept. RESOLVED: reopened to OPEN (status and `resolved_at` only, nothing else) by one conditional statement, only for a NEW inbound message whose effective time is later than `resolved_at`; never for a duplicate, a delayed older message, a reaction, or a RESOLVED conversation with no `resolved_at` (there is no instant to compare). A reaction is stored but does not change `last_message_at`, `last_inbound_at` or status (whether a reaction opens the service window is unresolved, G0); if a reaction has to create the conversation, `last_inbound_at` stays NULL. System messages never reach the handler (ingest stores them as ignored `OTHER` events) and are refused with `system_message_unsupported` if one did.
- **Timestamps.** `messages.occurred_at` is the provider timestamp exactly (epoch seconds, a positive integer inside the `Date` range, otherwise the permanent `invalid_timestamp`; never clamped). All derived activity (`last_message_at`, `last_inbound_at`, reopening, the contact's seen window) uses `effectiveActivityTime()` from `time.ts` (provider time capped at receipt + 5 minutes) and only moves forward (`GREATEST`). Future and stale timestamps are flagged (`webhook.timestamp_anomaly`, reason code only).
- **Message types** (`messages.type` is open text): TEXT, IMAGE, VIDEO, AUDIO (+ `voice`), DOCUMENT, STICKER (+ `animated`), LOCATION, CONTACT, INTERACTIVE (`button_reply`, `list_reply`), BUTTON, FLOW (`nfm_reply`), REACTION, and UNKNOWN for anything else (`unsupported`, `order`, future types: only `rawType`, `unsupported_type` and up to three `{code, title}` errors are kept). Only documented fields are read, into whitelists; nothing unrecognized is stored. The shape of a Flow reply (`nfm_reply`) is unresolved in the evidence register, so only the scalar fields actually present are kept, as bounded opaque strings, and the response is never parsed. `body` is the text, caption, title or location name; `content` holds the per-type object.
- **Sanitization and limits.** NUL and lone surrogates are removed (Sinhala, Tamil, emoji and ZWJ are preserved exactly; message text is not normalized). Text-like fields are cut to their limit by code points (text 4096, captions 2048, filenames 255, titles 256, descriptions 1024, location address 1024, shared contacts: 10 contacts, 5 phones and 5 emails each). A field beyond **four times** its limit is not a WhatsApp message and fails permanently with `content_too_large`; so does stored `content` above 32 KiB. The authenticated raw delivery stays in `webhook_requests` for investigation. Nothing logs message content or identifiers.
- **Media.** Image, video, audio, document and sticker messages store the metadata Meta supplies (media id, MIME type, filename, SHA-256, caption, `voice`, `animated`) in `content` and one `message_attachments` row with `storage_status = PENDING` ("provider media exists, not downloaded"), unique per message and media id. The provider's temporary download `url` is **not stored** (it expires within minutes and no column exists for it). Media without an id produces no attachment row. Nothing is downloaded and no Meta endpoint is called.
- **Replies.** `context.id` is stored as `reply_to_wamid`. `reply_to_message_id` is set only if that wamid exists in the SAME conversation (the composite foreign key allows nothing else); otherwise it stays NULL and the message is still stored. When a message arrives, replies waiting for its wamid in the same conversation are linked (never across conversations, accounts or organizations, never to itself, never over an existing link).
- **Click-to-WhatsApp attribution.** A referral on a NEW message becomes one `lead_attributions` row for that contact and message, with `lead_id` NULL: `source_type` META_AD only for the documented `ad` (Facebook versus Instagram is not guessed; anything else, or only a `source_url`, is REFERRAL with the original value kept in `provider_data`), `ctwa_clid` exactly as sent (it may be absent), `source_url`/`source_id`/`headline`/`body`/`media_type`, `media_url` from `image_url` (else `video_url`), `received_at` = when we received the event. `provider_data` is a small flat record (thumbnail url, welcome-message text, unrecognized scalar properties, at most 20, bounded; nested values are dropped). **A referral is attribution evidence only: no lead, student or marketing consent is created.** _Limitation:_ the table has no uniqueness on `message_id`, so "one attribution per message" is guaranteed by the application (written only by the call that inserted the message, behind a `NOT EXISTS` guard), not by the database. A partial unique index on `(organization_id, message_id)` would make it a database guarantee; that needs a migration and is not part of this checkpoint (blocker 21).
- **Archived contacts.** A message for an archived contact is stored for that contact; `archived_at` is never changed. No constraint of the existing schema prevents this.
- **Identity failures are permanent and visible.** The 4A resolver's permanent errors pass through unchanged. In particular a phone-only message for a BSUID-established contact becomes a `DEAD` event with `phone_only_identity_ambiguous` and writes nothing. Such events need manual review and a replay tool before production (blocker 22).
- **Transaction safety and fencing (verified, with one finding).** Every write uses the worker's transaction (one savepoint, no second connection), so a handler exception, a constraint violation inside the handler, a deferred-constraint failure at COMMIT and a lost lease all roll back contact, alias, conversation, message, attachment and attribution together with the event. Finding: the handler's rows reference the `webhook_events` row through foreign keys, which takes a `FOR KEY SHARE` lock on it, and the queue's reclaim (`FOR UPDATE SKIP LOCKED`) skips locked rows. So an event cannot be reclaimed while its worker is mid-transaction with domain writes; a worker that lost its lease before writing sees the committed message, writes nothing, and its completion is refused.

## Implementation notes (checkpoint 4C: STATUS processing)

`src/modules/whatsapp/status/` (`status-map.ts`, `handler.ts`) plus two small changes to existing code. **No migration, no new table, no new status system:** the handler reuses the Phase 02 operations `recordMessageStatus` and `resolveStatusEventsForMessage` (append-only `message_status_events` plus the priority-based cache on `messages`). The handler is `handleMessageStatus(tx, event, context)`; the registry `statusHandlers = { STATUS }` is passed explicitly by tests (MESSAGE + STATUS). **Nothing starts a worker**; IDENTITY and OTHER events stay unclaimed.

- **Order of operations (pinned by a static test).** Map and validate the stored envelope; verify the routed account is ACTIVE for the event's organization; take the transaction-scoped advisory lock `wa-message:{organization}:{account}:{wamid}` (the same key the inbound handler uses); call `recordMessageStatus` once. The organization and account come only from the trusted event row, never from the payload. The handler never completes the event; the queue's fenced update does, in the same transaction.
- **Mapping.** `sent`, `delivered`, `read`, `failed` become SENT, DELIVERED, READ, FAILED. `played` and unknown values are IGNORED at ingest (`status_not_mirrored`) and never claimed; if one reaches the handler directly it is the permanent `unsupported_status`. `statuses[].id` is an opaque wamid scoped to the routed account (bounded; `invalid_status` if missing, empty or too long). The recipient (`recipient_id`, `recipient_user_id`) is never read: a message is never found by phone number or BSUID, and a status never creates a contact.
- **History and idempotency.** Each observation is one row `(organization, account, wamid, status, occurred_at)` with the source webhook event; the existing unique key plus `ON CONFLICT DO NOTHING` makes redelivery, a retry after a crash, a second event for the same observation and two workers racing write exactly one row and leave the cache and `updated_at` unchanged. The same status at a different provider time is a different observation.
- **Out of order.** The cache moves only if the new priority is strictly higher (NULL < SENT < FAILED < DELIVERED < READ), so a late lower-priority status never regresses it and the final cache is the same for every arrival order (all 64 ordered selections of the four statuses are tested). The history always keeps the real provider times. FAILED has a lower priority than DELIVERED/READ by the approved Phase 02 policy: a delivery that arrives after a failure supersedes it and clears the cached error, the history keeps both. This was not changed.
- **Status before the message.** Kept with `message_id NULL`; no message, conversation or contact is fabricated; `resolveStatusEventsForMessage` links the rows and applies the best one when the outbound message exists. **Contract for the future outbound writer:** take the per-message advisory lock above before inserting an outbound message, and call `resolveStatusEventsForMessage` in the same transaction. A test holds the lock with an uncommitted message and proves the status handler waits and then links.
- **Direction safety (change to a Phase 02 operation).** `recordMessageStatus` previously matched any message with the wamid. It now selects the direction: a wamid that belongs to an INBOUND message is never linked and never updated (the observation is kept with `message_id NULL` and logged as `inbound_message_wamid`), and `resolveStatusEventsForMessage` returns unless the message is OUTBOUND. Lookups remain scoped by organization and account, so the same wamid on another account or organization is independent.
- **Timestamps.** The provider time (epoch seconds, positive, inside the `Date` range, via `parseProviderTimestamp`) is stored as sent; otherwise the permanent `invalid_timestamp` and nothing is written. It is never clamped. Future (> 5 min after receipt) and stale (> 8 days) values are logged as `timestamp_future` / `timestamp_stale`. Future-timestamp exposure of the cache: the cache DECISION uses priority, not time, so a far-future status cannot block a later real one; the only place a provider time reaches the message is the display field `messages.latest_status_at` (blocker 23). Statuses never change `last_inbound_at`, `last_message_at`, `last_outbound_at`, a conversation's status or `resolved_at`, so they cannot extend the customer-service window or reopen a conversation (tested by comparing every conversation row before and after).
- **Failed details.** Only the first `errors[]` entry's `code` (<= 64) and `message` (falling back to `title`, then to `error_data.details`; <= 500) are kept, NUL-stripped, and only for `failed`; `href`, the rest of `error_data` and further entries are dropped. Logs carry fixed fields only (event id, organization, account, type, reason): never wamid, phone, BSUID, error text or payload.
- **Transaction safety (verified).** A handler exception, a database error while inserting the history row, a deferred-constraint failure at COMMIT and a lost lease all roll back the history row and the cache together with the event's state. The same finding as 4B applies: once the history row exists it references the webhook event, so the event cannot be reclaimed mid-transaction; a worker that lost its lease before writing sees the committed row and its completion is refused. A duplicate writes no row and takes no such lock, which is harmless because it changes nothing.
- **Mutation checks.** Removing organization/account scoping, the priority check, `ON CONFLICT`, the direction check, the account check or the per-message lock; fabricating a message for an orphan; extending conversation activity from a status; writing on a second connection; and swallowing a failed write each fail at least one real-PostgreSQL test and a static guard.
- **Unverified shapes.** The `sent` and `read` status JSON are synthetic fixtures (no official example retrievable, G0); `delivered` and `failed` are official-example-derived. The handler reads only `id`, `status`, `timestamp` and `errors[0]`.

## Implementation notes (checkpoint 5A: standalone worker)

`src/modules/whatsapp/worker/` (`config.ts`, `registry.ts`, `loop.ts`, `run.ts`, `policy.ts`, `errors.ts`), the entry script `scripts/whatsapp-worker.ts`, `npm run whatsapp:worker`, and three small changes elsewhere (`createWorkerDatabase` in `src/db/client.ts`, an optional `stopSignal` in `processWebhookBatch`, an optional event-type filter in `readQueueStats`). **No migration, no new table, no second queue**: the worker is a loop around the existing `processWebhookBatch`. It calls neither Meta nor any network service and sends nothing.

- **Opt-in, fail closed.** It starts only when `WHATSAPP_WORKER_ENABLED` is exactly `true`. Unset, empty or `false`: it prints an explanation, exits 2 and opens no database connection at all. Any other value (`TRUE`, `1`, `yes`) is a refusal too (exit 2, the message names the variable, never a value). Nothing starts it automatically: not the web server, the build, migrations, tests, CI or the webhook route; there is no cron route, no `instrumentation.ts`, no lifecycle hook (a static test pins the one script and scans for the rest).
- **Registry.** `webhookWorkerHandlers` is a frozen literal with exactly `MESSAGE -> handleInboundMessage` and `STATUS -> handleMessageStatus`. No no-op handler exists and `IDENTITY` and `OTHER` have no entry, so such events are never claimed (they stay as ingest stored them). Tests insert real `OTHER` and `IDENTITY` events beside processable ones and show they keep `attempts = 0` and no lock.
- **Configuration.** `DATABASE_URL` (a postgres URL), optional `WHATSAPP_WORKER_BATCH_SIZE` (1 to 100, default 20) and `WHATSAPP_WORKER_CONCURRENCY` (1 to 8, default 2). Lease (120 s), handler budget (60 s), statement timeout (15 s), 8 attempts and the retry backoff are the queue's and are not configurable here. No Meta credential is read. Problems name keys only.
- **Start-up checks.** `SELECT 1`, then every table the handlers use must exist. An unmigrated database (the developer database currently has zero tables) ends in exit 2 and `schema_not_ready`; nothing is created or migrated. A wrong password, a missing database, or missing privileges are configuration errors (exit 2, not retried); an unreachable server is retried.
- **Polling.** An empty poll waits 500 ms, doubling to 5 s (+/-20% jitter); a poll that found work polls again at once, so a backlog drains without waiting and an idle worker costs one claim query per 5 s. A queue-depth line (`worker.stats`: pending, processing, failed, dead, held, ignored, expired leases, oldest due age for the types it can claim) is logged at start and then once a minute.
- **Concurrency.** Each lane claims one event immediately before running it (existing behaviour), at most `concurrency` handlers run at once, a batch is at most `batchSize` events, and the pool has `concurrency + 2` connections with a 10 s connect timeout. Tests measure the peak (2 by default, 1 when set).
- **Account state and tenant routing** are exactly the queue's: a PENDING account holds the event (`UNROUTABLE`), DISABLED or archived ignores it, routing columns are never rewritten, and the handlers re-check the account inside their own transaction. The worker never requeues, activates, replays, or re-homes anything; re-activating an account does not release held events (tested). That remains an operator decision for a later checkpoint.
- **Database trouble** (connection refused or reset, terminated backends, too many connections, an outcome that could not be recorded) is the worker's own concern, not an event failure: it waits 1 s doubling to 30 s, logs `worker.database_unavailable` (a short code, never the message), logs recovery, and exits 1 after 5 minutes without a successful poll. Individual events keep the queue's retry/dead-letter rules; there is no second retry mechanism. A crash mid-event leaves a leased `PROCESSING` row that another worker reclaims after 120 s; idempotency (message unique key, status history key, advisory locks) prevents duplicate rows (tested with `SIGKILL` of the real script, with two real processes on one queue, and with the worker's connections killed repeatedly while it processes 40 events: 40 messages, none lost, none duplicated, none processed without its rows).
- **Shutdown.** `SIGTERM` and `SIGINT` abort one signal: the loop stops claiming (also inside a running batch), in-flight handlers finish within their own budget, the pool is closed, exit 0. Past `handler budget + 10 s` the process gives up, exits 1 and the leases expire normally. Tests run the real script: an in-flight event (held by an advisory lock) finishes after `SIGTERM` while the events behind it stay untouched. Run it directly (`node --import tsx scripts/whatsapp-worker.ts` or `tsx`) under a supervisor: `npm run` forwards `SIGINT` from a terminal but a `SIGTERM` sent to `npm` alone may not reach the script.
- **Exit codes.** 0 clean stop; 1 fatal runtime (outage limit, shutdown deadline, uncaught exception); 2 refused (disabled, invalid configuration, unmigrated database, wrong credentials or database).
- **Logging.** Only the fixed-field `emitWebhookLog` (`worker.started`, `worker.stopping`, `worker.stopped` with totals, `worker.stats`, `worker.database_unavailable`, `worker.database_recovered`, `worker.fatal`, plus the queue's per-event and per-batch lines). No payload, message text, phone number, BSUID, token, secret, database URL, or provider id appears (a test greps the real process output for planted values). An uncaught exception logs one fixed line, never a stack.
- **A drizzle-orm bug the tests found.** drizzle-orm 0.45.3 runs `begin` outside the `try/finally` that releases the pooled client; a connection that dies exactly then leaves the client checked out for ever, a pool slot is lost and `pool.end()` never resolves. A worker meets this after a database restart. `createWorkerDatabase` therefore releases a still-held client one second after its connection ended (a later normal release is a no-op), and it handles `error` on checked-out clients (otherwise Node treats it as an uncaught exception and the process dies). The shared `getDb()` pool used by the web application is unchanged. Tests: a deterministic reproduction (fails without the guard), and the repeated-kill chaos test.
- **Mutation checks.** Registering a no-op `IDENTITY` handler, running without the opt-in, ignoring account state, claiming unsupported types, removing organization/account filters, writing outside the worker transaction (status and inbound), skipping lease-owner fencing, marking failed events PROCESSED, ignoring the stop signal, removing the client error listener, skipping the schema check, polling without waiting, ignoring the stop signal in the loop, and removing the begin-leak guard each fail at least one test; every mutation was restored byte for byte.
- **Not done here (deliberately):** deployment or supervision configuration, account onboarding or activation workflow, requeue/replay tooling, identity-change handling, outbound messages, media download, retention. See blockers 26 to 29.

## Consequences

- Migration `0002` changes `webhook_requests` (drops `raw_payload`, adds `raw_body`, `ingest_status`, `ingest_error_code`), `contacts` (nullable `wa_id`, `username`) and adds `contact_bsuids` (23 tables). `ADD COLUMN raw_body ... NOT NULL` assumes `webhook_requests` is empty, which holds everywhere because nothing writes it yet; on a non-empty table the migration fails safely and atomically (see the precondition section above).
- A contact must have a `wa_id` or at least one `contact_bsuids` row. The database cannot express that across tables; the single contact-creation code path, a database test and a tripwire query in the operator queue-status tool enforce it.
- `WEBHOOK_EVENT_TYPES` gains `IDENTITY` and `MESSAGE_TYPES` gains `REACTION` (TypeScript only; both columns have no CHECK).
- Open after this checkpoint: H1 (identity delivery), H2 (old/new BSUID overlap), H3 (multi-sender), the wire form of non-ASCII payloads, reaction versus the service window; see the evidence register. Identity handling must not be built until H1 is closed.
