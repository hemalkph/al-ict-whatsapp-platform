# Pre-production blocker register

What Phase 03 (authentication, memberships, authorization, staff management, browser E2E) knowingly does **not** solve. Green unit, database and browser suites do not close any of these. Each needs an owner and a decision before real users or real WhatsApp traffic are involved.

| #   | Blocker                                                                                    | State today                                                                                                                                                                                                                                                                                                                         | Needed before production                                                                                                                                                                                                                                                                                                                                            |
| --- | ------------------------------------------------------------------------------------------ | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 1   | Trustworthy production client-IP propagation                                               | The database rate limiter keys on the IP Better Auth derives from `x-forwarded-for`, and Next adds that header from the socket address when it is absent. Behind a proxy or CDN the value is whatever the edge forwards, and a client may supply its own. The browser E2E proves the limiter is wired in; it cannot prove IP trust. | Decide the topology, configure the trusted proxy header(s) explicitly (Better Auth `advanced.ipAddress.ipAddressHeaders` and `trustedProxies`, verified in the installed version) so only the edge-set value is used, strip client-supplied forwarding headers at the edge, and test it. Until then limiter keys can be spoofed or collapse onto the proxy address. |
| 2   | WAF / platform rate limiting                                                               | Only the in-app database limiter exists, and only on Better Auth's HTTP endpoints (server-side `auth.api` calls bypass it).                                                                                                                                                                                                         | Platform or WAF limits in front of `/api/auth/*`, `/api/account/*` and `/api/staff/*`, with per-IP and global ceilings.                                                                                                                                                                                                                                             |
| 3   | Rate limiting and hardening of authenticated password-change and password-reset routes     | `/api/account/change-password` and `/api/staff/*/reset-password` have no limiter of their own; they need a valid session (and `staff.manage` for resets) but a stolen session could guess the current password at full speed.                                                                                                       | A per-user (not only per-IP) limiter or lockout on current-password verification, and a decision on re-authentication ("fresh session") for administrator resets.                                                                                                                                                                                                   |
| 4   | Four moderate `npm audit --omit=dev` findings (`drizzle-kit` / `@esbuild-kit` / `esbuild`) | Reported through `better-auth`'s optional `drizzle-kit` peer. Dev-time tooling only, not in the runtime bundle. Documented, not forced: `npm audit fix --force` is not acceptable.                                                                                                                                                  | Re-check on each dependency update; resolve when a compatible `drizzle-kit` / `better-auth` release removes the old esbuild, or record an accepted-risk decision.                                                                                                                                                                                                   |
| 5   | Multi-organization selector                                                                | One ACTIVE membership is used implicitly; zero is 403 and more than one is 409. Staff creation refuses existing identities, and administrators cannot reset or revoke shared identities.                                                                                                                                            | Only if multi-organization operation is enabled: the slug-in-route selector, an invitation flow the user accepts while authenticated, and platform-level handling for shared identities (ADR 0012).                                                                                                                                                                 |
| 6   | Stale provisioning-intent monitoring                                                       | `staff_provisioning_intents` never expire automatically (releasing one could let another organization claim a partial identity). A recovery CLI exists (`auth:intents`); nothing alerts when an intent is stuck.                                                                                                                    | A scheduled check or alert on intents older than a threshold, and an on-call runbook step (`docs/RUNBOOK_AUTH.md`).                                                                                                                                                                                                                                                 |
| 7   | Email / self-service password recovery                                                     | No email infrastructure. The public reset surface is closed. Recovery is an administrator reset (exclusive identities only) or the operator CLI.                                                                                                                                                                                    | When email exists: verified, rate-limited self-service reset and email verification, designed with the shared-identity rules in ADR 0012.                                                                                                                                                                                                                           |

## Also still open (lower severity, documented elsewhere)

- Intent-recovery clock-skew tolerance is 5 s (`CLOCK_SKEW_TOLERANCE_MS`), a tripwire rather than the primary ownership guard.
- RLS is deferred (ADR 0012, RLS decision); runtime/migration database role split belongs to the deployment milestone.
- Absolute session cap (beyond the 7-day sliding window) was left undecided.

## Phase 04 (WhatsApp webhooks): open items recorded at checkpoint 1

| 8   | Identity-change delivery unresolved (G0 item H1)                                                   | Official Meta pages contradict each other (a system message with only the new BSUID versus a separate `user_id_update` field versus a legacy `user_changed_number` page). The handler is **not designed**; no automatic `wa_id` mutation is allowed.                                                                                                                                                                                                                                                                                                                                                                                                            | Confirm in the real App Dashboard which fields are subscribable and observe a real identity change; then design the handler. | 9   | Raw webhook body retention                                                                         | `webhook_requests.raw_body` stores exact bytes with personal data; no retention job exists.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                     | Decide retention (and held-event exemption), build the job, and handle the Phase 02 `NO ACTION` provenance FKs (confirmed by test: deleting an event is blocked until `messages.source_webhook_event_id` and `message_status_events.webhook_event_id` are nulled first; `contact_bsuids` is not affected).                                                                                                                                                                       |

| 13  | Webhook endpoint abuse and log flooding                                                            | Invalid signatures are rejected without a database write, but each is a log line.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                               | Platform/WAF limits in front of `/api/webhooks/whatsapp` (extends item 2).                                                                                                                                                                                                                                                                                                                                                                                                       |

| 16  | BSUID aliases can be re-pointed by an UPDATE                                                       | `UNIQUE (organization_id, bsuid)` blocks a second alias row but not an `UPDATE ... | 17  | Migration 0002 must precede any webhook data                                                       | `ADD COLUMN raw_body bytea NOT NULL` (no default, no backfill) fails safely if `webhook_requests` already holds a row; proven with the real migrator.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                           | Deploy order: apply 0002, then the webhook route. | 18  | Stored webhook events are not processed yet                                                        | Ingress stores deliveries and per-item events (PENDING / held / ignored / dead). The queue/worker core, the requeue primitives and the inbound MESSAGE and STATUS handlers exist (checkpoints 3, 4B, 4C) but nothing runs them: no worker command and no activation or operator requeue operation. There is no IDENTITY handler. Held (`UNROUTABLE`) and ignored events, including every `system` message, wait for them.                                                                                                                                                                                                                                       | Worker, requeue/activation operations and handlers (later Phase 04 checkpoints); retention must exempt held events.                                                                                                                                                                                                                                                                                                                                                              |
| 19  | Public webhook endpoint hardening beyond the application                                           | The endpoint refuses oversize bodies (4 MiB, connection closed) and unverified deliveries without writing, but still reads up to 4 MiB per request before verifying the signature.                                                                                                                                                                                                                                                                                                                                                                                                                                                                              | Platform/WAF rate and size limits in front of `/api/webhooks/whatsapp` (extends items 2 and 13); trusted-proxy handling.                                                                                                                                                                                                                                                                                                                                                         |
| 20  | A client that disconnects early on a POST can make Next.js log `uncaughtException: Error: aborted` | Found by an E2E run. Every non-GET request that passes `src/proxy.ts` has its body cloned by Next.js; after the proxy returns, Next replaces the request's stream internals and drops the router's `error` listener, so a disconnect before the response is complete (with the body unread, for example an early 401/403) is logged as an uncaught exception (ECONNRESET). Next's own handler keeps the process alive and the E2E run saw the server keep serving. Real clients on poor networks can produce the same log line, and alerting on `uncaughtException` would then raise false alarms. The test suite no longer provokes it (see TESTING_STRATEGY). | Re-check on each Next.js upgrade (`node scripts/repro-next-body-clone-abort.mjs` reproduces it with Next's own `getCloneableBody`; when its "after-finalize, body unread" line turns clean, this item can be closed). Options to decide later, none implemented: keep API routes' early refusals from leaving the body unread, or take `/api/*` out of the proxy matcher (that reduces the proxy's defense in depth, so it needs a security review). Do not filter the log line. |
| 21  | One attribution per message is not enforced by the database                                        | `lead_attributions` has no uniqueness on `message_id`. The inbound handler guarantees one row per message in application code (written only by the call that inserted the message, behind a `NOT EXISTS` guard, mutation-tested), so a bug or a second writer could still duplicate it.                                                                                                                                                                                                                                                                                                                                                                         | A partial unique index on `(organization_id, message_id) WHERE message_id IS NOT NULL` would make it a database guarantee. Needs a migration and your approval; not done.                                                                                                                                                                                                                                                                                                        |
| 22  | Events that fail identity resolution need manual review and replay                                 | A phone-only message for a BSUID-established contact (`phone_only_identity_ambiguous`), and any message with an unusable sender identity, becomes a `DEAD` event and writes nothing. The raw delivery is kept.                                                                                                                                                                                                                                                                                                                                                                                                                                                  | An operator review and replay tool (needs `webhook.manage`); a retention policy that exempts `DEAD` events awaiting review.                                                                                                                                                                                                                                                                                                                                                      |
| 23  | Provider-supplied future time can reach `messages.latest_status_at`                                | A status keeps its provider timestamp as sent. The cached status follows priority, never time, so a far-future status cannot block a later one and cannot touch any conversation or service window, but `latest_status_at` (a display field) can hold a future time. Nothing derives a window or ordering from it today; the status handler flags such values with `timestamp_future`.                                                                                                                                                                                                                                                                          | Any UI or report that reads `latest_status_at` must treat it as display data (or cap it); never use it for window or SLA logic.                                                                                                                                                                                                                                                                                                                                                  |
| 24  | The outbound message writer does not exist yet                                                     | Statuses that arrive before an outbound message are kept with `message_id NULL`. Linking relies on the future writer taking the advisory lock `wa-message:{organization}:{account}:{wamid}` before inserting the message and calling `resolveStatusEventsForMessage` in the same transaction; without the lock a status processed during that window stays unlinked until the next reconciliation.                                                                                                                                                                                                                                                              | The outbound phase must implement and test that contract (the lock/handler interplay is already tested against a stand-in writer).                                                                                                                                                                                                                                                                                                                                               |
| 25  | `sent` and `read` status payload shapes are synthetic                                              | No official example of the `sent` or `read` status webhook could be retrieved (G0). The handler reads only `id`, `status`, `timestamp` and `errors[0]`, which `delivered` and `failed` examples confirm.                                                                                                                                                                                                                                                                                                                                                                                                                                                        | Re-check against a real delivery in the optional live smoke before production.                                                                                                                                                                                                                                                                                                                                                                                                   |
