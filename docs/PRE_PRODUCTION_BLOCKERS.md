# Pre-production blocker register

What Phase 03 (authentication, memberships, authorization, staff management, browser E2E) knowingly does **not** solve. Green unit, database and browser suites do not close any of these. Each needs an owner and a decision before real users or real WhatsApp traffic are involved.

| #   | Blocker                                                                                    | State today                                                                                                                                                                                                                                                                                                                         | Needed before production                                                                                                                                                                                                                                                                                                                                            |
| --- | ------------------------------------------------------------------------------------------ | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 1   | Trustworthy production client-IP propagation                                               | The database rate limiter keys on the IP Better Auth derives from `x-forwarded-for`, and Next adds that header from the socket address when it is absent. Behind a proxy or CDN the value is whatever the edge forwards, and a client may supply its own. The browser E2E proves the limiter is wired in; it cannot prove IP trust. | Decide the topology, configure the trusted proxy header(s) explicitly (Better Auth `advanced.ipAddress.ipAddressHeaders` and `trustedProxies`, verified in the installed version) so only the edge-set value is used, strip client-supplied forwarding headers at the edge, and test it. Until then limiter keys can be spoofed or collapse onto the proxy address. |
| 2   | WAF / platform rate limiting                                                               | Only the in-app database limiter exists, and only on Better Auth's HTTP endpoints (server-side `auth.api` calls bypass it).                                                                                                                                                                                                         | Platform or WAF limits in front of `/api/auth/*`, `/api/account/*` and `/api/staff/*`, with per-IP and global ceilings.                                                                                                                                                                                                                                             |
| 3   | Rate limiting and hardening of authenticated password-change and password-reset routes     | `/api/account/change-password` and `/api/staff/*/reset-password` have no limiter of their own; they need a valid session (and `staff.manage` for resets) but a stolen session could guess the current password at full speed.                                                                                                       | A per-user (not only per-IP) limiter or lockout on current-password verification, and a decision on re-authentication ("fresh session") for administrator resets.                                                                                                                                                                                                   |

| 5   | Multi-organization selector                                                                | One ACTIVE membership is used implicitly; zero is 403 and more than one is 409. Staff creation refuses existing identities, and administrators cannot reset or revoke shared identities.                                                                                                                                            | Only if multi-organization operation is enabled: the slug-in-route selector, an invitation flow the user accepts while authenticated, and platform-level handling for shared identities (ADR 0012).                                                                                                                                                                 |

## Also still open (lower severity, documented elsewhere)

- Intent-recovery clock-skew tolerance is 5 s (`CLOCK_SKEW_TOLERANCE_MS`), a tripwire rather than the primary ownership guard.
- RLS is deferred (ADR 0012, RLS decision); runtime/migration database role split belongs to the deployment milestone.
- Absolute session cap (beyond the 7-day sliding window) was left undecided.
